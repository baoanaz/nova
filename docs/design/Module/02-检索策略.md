## 0. 组件定位

一句话：**把一个自然语言/符号混合的查询，变成一组带证据标注、经过质量排序的候选切片**。

```text
输入                        本组件                              输出（给 03）
──────                    ──────────                          ──────────
query（中/英/符号混合）  →  轻路由 → 多路召回 → RRF          →  候选集（已排序、去重、
索引（01 产出的              → 图扩展 → Evidence Rerank           带 tier/reason/score/
  chunks_fts / vectors /                                           callPaths/gap 信号）
  edges / spec_blocks）
Fast/Deep 模式标记       →  Deep 额外：Gap 检查 → 定向二轮
```

**边界（不管什么）**：
- 不管切片与索引结构（01）
- 不管 ContextPack 字段组装与 token 预算裁剪（03——本组件给"原料"）
- 不管 LLM 调用与 prompt（04）
- 不管 MCP 协议与超时重试（05）

**兑现 01 的接口约定**（Module/01 §2.2 ④，逐项落实位置）：

| 01 的信号 | 本文消费位置 |
|---|---|
| doctype | §4.2 Spec 证据的保留与权重 + §4.5 rerank 特征 |
| spec_references | §4.4 图扩展第二种边（双向） |
| symbol_kind | §4.5 rerank 特征 + 传给 03 分列 |
| spec_references.stale | §4.5 rerank 降分 + §4.7 G4 缺口 |

## 2. 业界方案盘点

| 方案 | 代表 | 原理 | 对 nova 的评估 |
|---|---|---|---|
| 纯向量 RAG | 早期开源 RAG、多数 chat-with-repo | query embed → ANN → topK | 弱：标识符不敏感（"TokenService" 检索靠语义碰运气）、路径幻觉 |
| 纯词法检索 | grep / ripgrep / Zoekt(trigram) | 精确匹配/倒排 | 精确但无语义，"哪里处理过期"类查询失效 |
| **Hybrid + RRF** | GitNexus、Elasticsearch、Weaviate | 多通道各出排名，按名次倒数融合 | 【已验证】免分数归一化、可解释、20 行实现（Background/04 §5） |
| Hybrid + 加权分数融合 | 部分自研系统 | 各通道分数归一化后加权 | 分数尺度不可比（BM25 无界 vs 余弦有界），归一化是永远的坑 |
| GraphRAG（社区摘要式） | 微软 GraphRAG | 图+社区+LLM 摘要做 corpus 级问答 | 重、贵、离线索引；适合"整个仓库讲什么"不适合"这个函数谁调用" |
| HyDE / Multi-Query | LLM 查询改写家族 | LLM 生成假设答案/多视角查询再检索 | 每次查询多一轮 LLM 延迟，与 R1 冲突；Deep 模式 V1.5 候选 |
| 符号优先检索 | codegraph explore、GitNexus context | 符号解析 → 图 → 源码分组 | 【已验证】结构型问题最优路径（Background/02 §5、04 §9） |
| Cross-Encoder / LLM Rerank | 业界主流 rerank | 模型对 (query, doc) 对精排 | 准但贵且加延迟；V1 用确定性特征 rerank 替代，V1.5 可选接入 |

**结论**：Hybrid+RRF 做融合共识 + 符号/图做结构路径 + 确定性 Evidence Rerank 做最终质量——每个环节均有参考项目生产验证，组合是新的。

## 3. 主链路总设计

阶段命名（**架构表达口径，2026-09-15 统一**）：**Recall → Expand → Rank → Pack → Repair**，
即 **四级检索漏斗 + 单次 Evidence Repair Loop**。

| 阶段 | 解决的问题 | 代码位置 |
|---|---|---|
| **Recall** | 有没有找到 | `retrieval/`（exact / literal / inferred / bm25 / vector + RRF） |
| **Expand** | 有没有找到"周围" | `retrieval/expand.py`（calls 1-hop + spec_references 双向） |
| **Rank** | 谁最重要 | `retrieval/rerank.py`（确定性 16 特征，无模型） |
| **Pack** | 有限 Token 带什么 | `contextpack/assembly.py`（预算 / 配额 / 去重三招） |
| **Repair** | 有没有缺关键证据 | `retrieval/gap.py` + `engine._backfill_gaps`（**回路**，非一级） |

> **Repair 是回路不是层级**：它消费 Pack 的产物、只做定向补齐、不新增召回通道。
> 实测（93 条正例）触发 80% 而 coverage 提升仅 8 条（开销/收益 ≈ 6.4×），
> 但关掉它 MRR 降 0.011——**结构上只能是 Feed-back，不能写成"第五级排序"**。
> 数据见 `benches/results/param-sensitivity-2026-09-15.md` §4。

```text
                    Query（中文/英文/符号混合）
                          │
                 ┌────────▼────────┐
                 │  轻路由（4 分支） │  ← 分支数硬上限 4（R4 / D-14）
                 └────────┬────────┘
       ┌──────────────┬───┴──────────┬──────────────┐
       ▼              ▼              ▼              ▼
   [General]     [Structural]     [Docs]       [Symbol/Path]
   四通道并行     符号解析→图直查   Spec 证据加权   Explicit Exact
   基准配额       callers/trace    优先          直接进种子池
       │              │              │              │
       └──────────────┴──────┬───────┴──────────────┘
                             ▼
              ── 1 Recall ──  RRF (K=60)
                             │
                             ▼
                       Strong Seeds
                             │
              ── 2 Expand ──  Graph Expansion
              calls 1-hop + spec_references 双向边
              （tier=3，配额 ≤30%）
                             │
              ── 3 Rank ──── Evidence-aware Rerank（确定性，无模型）
                             │
                             ▼
                    候选集 → 03 组装 ContextPack
                             │
             ┌───────────────┴───────────────┐
             ▼ Fast                          ▼ Deep
      ── 4 Pack ──                    ── 4 Pack ──
         直接返回                 Evidence Repair Loop
                                  │ 命中缺口 → 定向补检（≤1 次）
                                  │ 只提池内候选、独立预算、标源
                                  ▼
                            重组装 → LLM（04 组件）
```

## 4. 各阶段详细设计

### 4.1 轻路由（Lightweight Routing）【吸收外部 AI 建议，D-14】

四个分支，**线性判断，一次通过**：

| 分支 | 判定信号（全部 deterministic） | 通道行为 |
|---|---|---|
| Symbol/Path | 查询含反引号包裹标识符 / 文件路径 / `::` 链 | Explicit Exact 直进种子池，其他通道配额减半 |
| Structural | 含"谁调用/调用链/影响/调用关系/caller/callees/trace/flow"+ 可解析符号 | 符号解析 → **图为主路径**（§4.4-b），向量通道可跳过 |
| Docs | 含"为什么/设计/架构/spec/文档/why/design/ADR"+ 无符号 | Spec 证据保留和权重提升（复用现有 BM25/Vector，不新增 Planner 通道），代码通道正常参与（验证用） |
| General | 以上皆非 | 四通道基准配额 |

**护栏（R4 的落地，写死在代码评审规则里）**：
1. 分支数上限 4，新增分支需要架构评审并修订 D-14；
2. 分支只改**通道配额与优先级**，不新增检索通道、不写业务关键词规则（"migration_history intent"这类东西永远不许出现）；
3. 路由失败/未命中任何分支 = General，安全兜底。

### 4.2 召回通道

**a) Exact 通道——Explicit 与 Inferred 分离【吸收外部 AI 建议，D-15】**

| 档位 | 判定 | 处理 |
|---|---|---|
| Explicit | 反引号包裹 `` `refresh_token` ``；含扩展名的路径 `src/auth/token_service.py`；`::` / `.` 标识符链 `TokenService::refresh` | 强种子：symbols 表精确/fqn 匹配，全量进池（≤20），rerank 大加分 |
| Inferred | 正则从自然语言抽取的驼峰/蛇形/SCREAMING（codegraph extractSymbolsFromQuery 模式） | 普通种子：top 20，rerank 小加分 |

理由【已验证：codegraph/ragcode 踩坑共识】：inferred 抽出 "refresh" 会同时命中 refreshUI/refreshCache/refreshConfig——它是"召回种子"不是"精确证据"。Explicit 才配得上 tier 0。

**b) BM25 通道（FTS5）——含 CJK 修正【D-20，修正 01 的缺陷】**

- 配额 top 50；查询语言无关，中英混合词全部进 FTS MATCH
- **CJK 分词**：unicode61 tokenizer 对中文**不分词**（整句成单 token，中文查询直接失效——这是本次评审 01 时交叉发现的缺陷）。方案：**索引与查询双侧同库分词**（服务端引入分词器作为独立模块：jieba 系，runtime 未定故模块化），分词结果空格连接后写 FTS；查询侧同一分词器预处理。备选：FTS5 trigram tokenizer（免分词但索引膨胀 ~3x 且丢失词权重语义）【权衡：选预分词】
- generated 文件（files.generated=1）不排除但在 rerank 降分（§4.5）
- **已同步修正 Module/01 §3.3 DDL**（tokenizer 行与修订记录）

**c) Vector 通道**：query embedding（中文直接 embed，模型天然多语，无需分词）→ LanceDB ANN → top 50。延迟主导项（50-200ms），全通道并行化后它决定下限；query embedding 短期缓存（同一 query 60s 内复用）。

**d) Spec 证据（SpecBlock 一等对象，D-42）**：对 `spec_blocks` 复用现有 BM25/Vector 召回接口，结果与代码候选统一进入 RRF 和 Evidence Rerank。SpecBlock 作为证据类型单独标记，但不新增第五套 Planner 通道。

- General 路由正常参与代码与 Spec 召回；Docs 路由提高 SpecBlock 的保留配额和 rerank 优先级。
- `doctype` 作为确定性权重信号，`agent-instructions`、`design`、`adr`、`readme`、`api` 等高信息密度文档优先。
- ContextPack 装填时，存在相关 SpecBlock 则至少保留 1-2 块，并与代码证据分列呈现。
- `spec_references` 继续作为 calls 边之外的弱扩展边，双向补充设计意图和实现位置。

### 4.3 RRF 融合（纯 RRF 立场，D-16）

```text
score(c) = Σ_通道 1 / (60 + rank_通道(c))
```

- **不加通道权重**【权衡】：加权 RRF 会重新引入"分数调参"复杂度；通道差异化全部交给 rerank 层，融合层保持极简可解释（"多通道共识"是它唯一的工作）
- 去重键：chunk_id（spec 块与代码块天然不同 id）
- 输出：RRF 池 ~120 候选（四通道配额去重后）

### 4.4 图扩展（双角色，D-18）

**a) 普通查询：图是扩展器**

```text
seeds = RRF 池中 top 20 的代码 chunk（取其 symbol）
每 seed：
  ├─ calls 边 1-hop：caller / callee 的 chunk 入池，tier=3
  └─ spec_references 双向边（01 兑现）：
      代码 seed → 引用它的 SpecBlock（带出"设计意图"）
      spec seed → 它提到的代码符号（带出"实现位置"）
防爆炸：扩展总量 ≤30 块；单符号 callers > 200 时按入口点评分截断 top 20
（入口点=无内部调用者+被导出，GitNexus entry-point-scoring 思想【已验证】）
```

**b) 结构型查询：图是主路径**

"Foo 谁调用？" / "A 到 B 怎么走？" / "改 X 影响哪里？"——不走向量→RRF→再图的全流程：

```text
符号解析（Exact 通道产物）
  → callers/callees：SQL 直查 edges（target|source, kind='calls'）
  → flow："A 到 B"：BFS 最短路径（codegraph named-symbol-flow 模式【已验证】）
  → impact：caller 闭包（限深 3，超限如实报告截断）
```

图结果直接作为主证据（tier=1，reason='structural'），BM25/Vector 仅作背景补充。

### 4.5 Evidence-aware Rerank（确定性，V1 内置，D-16）

**为什么 V1 就要有**（对 06 提案的修订）：RRF 只知道"谁被多通道喜欢"，不知道这是生成代码/测试/过期文档/图 2 跳——这些信号 01 全都给了，消费它们只需加减法，零模型零延迟。基准分 = RRF 分，特征表：

| 特征 | 分值 | 信号来源 |
|---|---|---|
| + Explicit symbol/path 命中 | +2.0 | Exact-Explicit（§4.2-a） |
| + query 符号名与 chunk 符号名精确等值 | +1.0 | Exact-Inferred |
| + 3 通道共识 | +0.5 | RRF 通道计数 |
| + 与 top-1 种子图连通（1 跳） | +0.5 | 图扩展记录 |
| + doctype ∈ {agent-instructions, design, adr, readme, api} | +0.8 | 01 doctype（D-13、D-42 兑现） |
| + 入口点 / 被导出符号 | +0.2 | symbols.is_exported |
| − generated 文件 | −1.0 | files.generated |
| − test fixture（非测试意图查询） | −0.5 | 路由分支参与判断 |
| − stale spec 引用 | −0.8 | spec_references.stale（01 兑现） |
| − fallback_block chunk | −0.5 | symbol_kind |
| − 图距离 2 跳 | −0.3 | 扩展深度 |
| − 合成边（provenance=synthesized）扩展而来 | −0.2 | edges.provenance |

分值为初始值，需 benchmark 校准（§7-2）。V1.5 起可选挂 cross-encoder/LLM reranker（接口预留，circuit breaker 回退本表，ragcode 模式【已验证】）。

### 4.6 EvidenceTier 语义修订（D-17，修正 Background/06）

**06 原表述**："最终选择时强制按 tier 排序（exact > keyword > semantic > graph）"——**废止**。

反例【吸收外部 AI 建议】：Explicit 命中无关 UI 模块的 `refresh()`（tier 0）vs BM25+Vector+图三通道同时支持的 `TokenService::refresh`（tier 2）——硬排序会把错的排前面。

**修正后的 tier 语义**：
1. **可信度元数据**：随候选进 ContextPack，供 03 标注、04 的 LLM 判断、以及用户 explainability（"这条证据为什么在"）
2. **装填资格线**：03 组装时 tier 3（图扩展）有配额上限（≤30%），防止低置信图扩展淹没直接命中
3. **rerank 强特征**：tier 参与 §4.5 打分，但**不是 ORDER BY**

### 4.7 Deep 二轮检索：Evidence Gap 驱动（D-19）【吸收外部 AI 建议，本文最高价值增量】

**原则：不预猜 intent，先搜一轮，根据证据缺什么再定向补**——与 60s Deep 定位匹配，与 ragcode 的 300 行正则 planner 路线彻底相反。

Gap 判定规则表（全部 deterministic）：

| # | 缺口信号 | 判定条件 | 补检动作 |
|---|---|---|---|
| G1 | 调用链断裂 | Structural 路由且种子已解析，但 callPaths 平均长度 <2 | 对 top 种子做 2-hop 定向图查询（不全量重跑） |
| G2 | 设计意图缺失 | Docs 路由或 query 含设计类词，但 spec evidence = 0 | SpecBlock 召回重检 + 首轮代码符号反查 spec_references |
| G3 | 无共识结果 | 首轮 top10 全部单通道命中（无任何双通道共识） | 用 top3 块的符号名/文件名构造扩展查询，重召回一轮 |
| G4 | 文档过时 | 命中带 stale 引用的 SpecBlock | 不触发二轮；进 MissingEvidence 警告（"文档引用的符号已不存在"） |
| G5 | 预算富余 | 03 组装后预算剩余 >30% 且存在被裁的 tier≤2 候选 | 放宽 limit 重组装（非检索动作） |

**二轮纪律**：G1-G3 任一命中才触发；最多 1 次迭代；二轮只补缺口对应通道；二轮结果进 rerank 统一排序（不直接插队）。

#### 4.7.1 Repair 的定位与防漂移约束（2026-09-15 追加）

> **Gap 只回答“当前 ContextPack 是否缺了回答这个 query 所必需的一类证据”，
> 不尝试理解整个问题。** Gap ≠ 第二个搜索策略，Gap = Evidence Completeness Check。

背景：这类机制后期极易演化成 G1 缺定义 / G2 缺 caller / G3 缺 config / … / G8 缺一堆，
最终变成**第二套路由器**。因此必须给 Repair 设硬约束，而不是靠“规则少一点”的自觉。

**R31（新增约束，与 R4 同级）——Repair 三条不变量（可测试，违反即 bug）**：

| # | 不变量 | 实测状态 |
|---|---|---|
| I1 | **只能把已在首轮候选池内的候选提升进包，永远不得引入池外候选** | 93 条 / 455 个补检候选 **零违反** |
| I2 | 不新增召回通道、不改排序键（结果必经同一 rerank） | 成立 |
| I3 | 独立小预算，不挤占首轮份额；每条补检证据标注来源 | 成立 |

I1 是**结构不变量**，比“规则数 ≤N”强得多：它让“Repair 变成第二套检索策略”在结构上不可能
——无论以后加多少条规则，**召回空间都不会因此扩大一分**。它同时自动否掉设计表里的 **G3**
（“构造扩展查询重召回”必然引入池外候选，按 I1 天然非法）。

**规则预算（R4 扩展到 Repair）**：Repair 规则同样受 R4 的“分支数硬上限”管辖——
新增/合并规则需架构评审并修订 **D-19**；不得以“只加一条”为由绕过。

**规则数量现状**：实现中只有 **G1（容器-成员断层）/ G2（文档锚点闭包）** 两条，
且二者判据同源（均为“已在包内锚点的确定性结构闭包”），可视为同一条规则的两个取景。
G3 未实现（按 I1 不合法，且无实测触发）；G4 已由 TASK-096 实现（进 MissingEvidence，
不触发二轮）；G5 属组装层（TASK-108 已把闸门改为优先级语义）。

**触发面偏宽是已知问题**（实测触发 80% 而 coverage 提升仅 8 条，开销/收益 ≈ 6.4×）：
实测四种候选闸门（仅 `answerable=false` / `truncated` / 首轮无命中 / 组合）**都会丢掉
大部分收益**（丢 2–6 条 / 共 8 条），因此**现在不硬收**，等 TASK-093 真实数据。
数据见 `benches/results/param-sensitivity-2026-09-15.md` §4。

**已知越界项（待清理）**：实现里有一处 `chain_priority`（优先补“包内成员的被调用方”）——
它无 query 谓词，但性质上属“推测哪类证据更该进包”，与本节原则相悖；
实测收益极小（2 个用例各 1 名，约 0.001 MRR），**建议删除**。

#### 4.7.2 参数不得基于现有测试集调（R29/R30 的实测依据）

2026-09-15 对四靶场 93 条正例做了参数敏感性扫描（`benches/param_sweep.py`），
结果**直接支持 R29/R30 的冻结纪律**：

| 对方建议要调的参数 | 实测 ΔMRR | 结论 |
|---|---|---|
| `seeds` 10/20/40 | **±0.0000** | 敏感度为 0 |
| `max_expanded` 15/30/60 | **±0.0000** | 敏感度为 0 |
| `tier3_ratio` 0.30/0.45 | **±0.0000** | 敏感度为 0 |
| `single_file_ratio` 0.25/0.40 | **±0.0000** | 敏感度为 0 |
| `score_ratio` 0.40→0.15 | +0.0021 | 噪声内（阈值 0.005） |
| `docs_ratio` 0.10→0.05 | +0.0035 | 噪声内 |

**这意味着：当前瓶颈不是参数值，是测试集与真实数据（TASK-093）。**
93 条人工题下改一条用例的排名即可动 MRR 约 0.002，拟合出的值换一批题即反向。
同一次扫描还**反向验证了四项已有决策**（关掉即显著变差）：向量语义特征 −0.033、
测试夹具抑制 −0.018、`RRF_BASE_SCALE` 定档 ×100 −0.021、Repair 回路 −0.011。

### 4.8 快慢模式共享管线

Fast = §3 主链路一次到底。Deep = Fast 全流程 + §4.7 Gap 检查 + 定向二轮 + 重组装。**不分叉成两套检索代码**（D-10 兑现：search_context / ask_project 共用一条管线，分叉点在 03 之后）。

## 5. 时序与性能预算

| 阶段 | Fast | Deep |
|---|---|---|
| 轻路由 | <1ms | <1ms |
| 召回（并行，Vector 主导） | 50-200ms | 同左 |
| RRF + 图扩展 | 20-60ms | 同左 |
| 确定性 Rerank | <5ms | 同左 |
| Gap 检查 | — | <5ms |
| 定向二轮（≤1 次） | — | 50-300ms |
| 03 组装 | ~20ms | ~20ms |
| LLM（04） | — | 2-5s |
| **合计** | **~0.3-0.5s**（R1 目标 <2s 达标，10s 上限余量 20x） | **<10s**（R1 目标 60s 上限余量 6x） |

慢路径风险：embedding API 抖动（200ms→2s）——query 缓存 + 超时降级为 BM25+Exact 双通道（向量缺失时 RRF 自动退化为双通道融合，结果照出，confidence 降级，GitNexus #1489 优雅降级模式【已验证】）。
