# Module 03 — 上下文组装（组件详细设计）

> 系列：nova 组件详细设计（Module/），本文是第 3 篇，引擎流水线的下游。
> 依赖：消费 02-检索策略 的候选集（已排序、带 tier/reason/score/callPaths/gap 信号）与 01 的 freshness 信号；输出 ContextPack 给 04-AI总结（Deep 模式）或直接渲染给 05-MCP（Fast 模式）。
> 状态：草案（待评审）。最后更新：2025-09-09。
> 修订记录：2025-09-09 v1 — 覆盖初版（外部 AI 思考稿），吸收其证据分列/去重压缩/单文件上限/双层合同（见 §9 对照）；裁决 Deep 预算为 12K 硬顶（§4.2，与其 20-50K 建议不同，理由见文中）；敲定 02 §7-4 的 callPaths 格式（§3）。

## 0. 组件定位

一句话：**把 02 送来的候选证据，组装成预算内、结构化、可引用、诚实标注缺口的 ContextPack**。

```text
输入（02 的候选集）             本组件                        输出
──────────                 ──────────                    ──────
排序后的候选 chunks     →   证据分列（code/docs/flows）  →  ContextPack（内部 JSON 合同）
callPaths + gap 信号    →   去重压缩（三招）                 ├─ Fast：渲染 Markdown → MCP 直接返回
freshness（01）         →   预算装填（贪心+配额）             └─ Deep：整包传 04 做 grounded 总结
                            渲染（Markdown，双层共用）
```

**边界**：不管检索与排序（02）；不管 LLM 调用（04）；不管 MCP 协议（05——本组件给它的只是"渲染函数"）。

**核心原则（本组件一句话）**：
> 检索解决"找到什么"，组装解决"AI 最终应该看到什么"——用最少的 token 交付足够、准确、可验证的上下文。

## 2. ContextPack 正式合同（v1，D-21）

**双层合同**：内部结构化 JSON（引擎各组件间流转、04 消费）+ 对外 Markdown（05 的 MCP 响应、04 的 evidence 渲染）——两层共用同一 formatter，杜绝两套渲染逻辑漂移。

```json
{
  "query": "token 过期后在哪里刷新？",
  "mode": "fast | deep",
  "answerable": true,
  "confidence": "high | medium | low",
  "freshness": {
    "indexedAt": 1760000000,
    "staleFiles": [],          // 01 报告：已变更未重索引
    "indexingFiles": []        // 05 报告：已上传仍在索引队列
  },
  "evidence": [                // 代码/测试证据（单一引用编号空间）
    {
      "id": "E1",              // citation id，包内唯一且稳定
      "type": "code | test",
      "path": "src/auth/token_service.py",
      "symbol": "TokenService.refresh",
      "lines": [45, 82],
      "content": "…带行号原文…",
      "score": 0.031,
      "evidenceTier": 0,
      "reason": "explicit symbol + BM25",
      "elidedLines": 0
    }
  ],
  "docs": [                    // spec 证据（01 SpecBlock 装填产物）
    {
      "id": "E7",              // 与 evidence 共用编号空间（citation 回验统一）
      "type": "spec",
      "path": "docs/auth.md",
      "headingPath": "认证 > Token Refresh",
      "doctype": "design",
      "lines": [30, 52],
      "content": "…",
      "reason": "spec vector + doctype=design",
      "staleRefs": ["LegacyToken.rotate"]   // 引用了已删除符号 → 文档可能过时
    }
  ],
  "flows": [                   // 调用链（02 产出，格式在此敲定——02 §7-4）
    {
      "id": "F1",
      "nodes": [ { "symbol": "AuthMiddleware.verify", "path": "src/mw.py", "line": 88 },
                 { "symbol": "TokenService.refresh",  "path": "src/auth/token_service.py", "line": 45 },
                 { "symbol": "TokenStore.rotate",     "path": "src/store.py", "line": 210 } ],
      "truncated": false       // 图深度截断时如实标注
    }
  ],
  "missingEvidence": [
    { "code": "graph_boundary", "message": "调用链在动态 dispatch 处中断", "symbol": "Plugin.execute" }
  ],
  "nextQueries": [ "TokenService.refresh 的调用方有哪些" ],
  "budget": { "usedTokens": 7200, "hardCap": 12000, "truncated": false, "omittedCount": 3 }
}
```

**合同要点**：
1. **evidence 与 docs 共用 E 编号空间**（不分 E/D 前缀）——04 的 citation 回验只需验证 `[E\d+]` 存在性，一种规则管所有证据类型。flows 用 F 编号。
2. answerable / confidence 由本组件判定（规则见 §4.4），不由 LLM 自评。
3. token 估算：chars/4 近似（无 tokenizer 依赖，标注 approximate——ragcode budgetTrace 同款妥协【已验证】）。

## 3. 证据分列与去重压缩

**证据类型分列**（吸收外部建议，对齐 Task.md 四分证据）：

```text
CODE（含 TEST 子型）  /  SPEC（docs 数组，doctype 保留）  /  FLOW（flows）  /  GRAPH RELATION（V1 预留字段）
```

分列的直接消费者是 04：prompt 渲染时 code 与 spec 分节呈现，LLM 才能执行"Code=实现 / Doc=意图"的区分纪律（Task.md §16）。

**去重压缩三招**（吸收外部建议 + 06 提案合并）：

| 招 | 规则 | 例 |
|---|---|---|
| 相邻区间合并 | 同文件两 chunk 行距 ≤10 → 合并为一个区间 | L40-70 + L65-90 → L40-90 |
| 同符号聚合 | 同 symbol 多 chunk（重载/分段）只保留 rerank 分最高者，其余计入 omittedCount 并在 reason 注明 | Foo::run#1/#2 → 留其一 |
| skeleton 降级 | 单 chunk >300 行且装填超限时：签名 + 命中行 ±15 行 + elidedLines 计数 | 大函数不撑爆预算 |

> **TASK-MCP-BUDGET（2026-09-16）**：二轮补检的**首位候选豁免**该降级（其余候选不变）。
> 首位 = 补检池里排第一、也是优先级最高的那条；实测它是唯一能回答该问题的长方法
> （``process_with_streaming`` 199 行 / 2016 token）时，降级成“签名 + 15 行”恰好丢掉问题要问的正文。
> 公平上限的原本目的是“防一个大调度器独吞配额、让后面 13 个成员无处可放”
> （目标为**多个小成员**的场景）；当首位目标本身就是唯一答案时，让位换不来任何东西。

## 4. 预算装填算法（D-22）

### 4.1 装填主流程

```text
输入：02 候选集（rerank 分降序）
预算 = hardCap − 框架开销（query/freshness/missing 等元数据 ≈500 tok）
单文件上限 = 2500 tok（**绝对值**，TASK-MCP-BUDGET；不随 hardCap 缩放）   （A2）
tier3 配额  = 30% × 已用预算                    （A3）
spec 份额   = 950 tok（**绝对值**，TASK-MCP-BUDGET）                      （R21）
spec 保底   = 相关 spec 存在时至少装 1-2 块      （02 §7-3 的装填侧回答：分池配额在装填层做）

for c in candidates（分数降序）:
    if 预算耗尽: truncated=true; break
    if 文件用量 + est(c) > 单文件上限:
        尝试 skeleton 降级；仍超 → skip（omittedCount++）
    if c.tier==3 and tier3用量 + est(c) > 配额: skip
    应用去重三招 → 装入对应数组（evidence / docs）
flows 直接收纳（02 已做图侧截断），只计 token 不参与竞争
```

### 4.2 预算裁决：Deep 为什么不是 20-50K（与外部建议的分歧点）

外部建议稿提出 Deep 20-50K。**不采纳**，理由：

1. 总结模型已定为 deepseek-v4-flash 类（D-11）——flash 档模型在长输入下有效注意力衰减明显，20K+ 的 evidence 只会稀释而不增益【权衡：若未来换 deepseek-reasoner 级模型可上调配置】
2. ask_project 的价值是压缩而非搬运：证据 + 1-3K 回答 ≈ 一次 15K token 调用，flash 定价下成本可忽略；50K 输入则每次调用成本 ×4 且质量不升反降
3. 硬顶倒逼装填层做好"少而准"——这与 nova 的核心指标 Context Acquisition Cost 同向（Task.md §23）

> **TASK-MCP-BUDGET 修订（2026-09-16）**：原定 Fast 10K / Deep 12K。实测（cockpit-agents-py
> golden 38 题 + cockpit-agents-server 真实链路题）表明：**同样的题目在 10K/14K/16K 三档下
> recall/MRR 逐位相同**（0.861/0.861/0.562），而省略行数从 936 降到 665——即预算加大没有
> 换来噪音，只换来了“长函数更完整”。故调整为 **Fast 14K / Deep 16K**。
> 关键前提：单文件上限与 spec 份额必须**锚定绝对值**，否则按比例放大会让文档/单文件挤掉真实目标
> （实测 16K 按比例时``cockpit-0037`` 命中从 rank 3 滑到 rank 6，recall@5 0.861→0.833）。
> 同时修复：``Engine.search_with_trace`` 此前两次 ``assemble`` 都硬编码 ``mode=MODE_FAST``，
> 导致 ``DEEP_BUDGET`` 从未生效（Deep 实际按 Fast 预算装填）。

### 4.3 Fast 与 Deep 的装填差异

| 维度 | Fast | Deep |
|---|---|---|
| hardCap | 14K（默认；TASK-MCP-BUDGET） | 16K |
| flows | 包含（02 图扩展产物） | 包含（含二轮 G1 补充的 2-hop 链） |
| gap 信号 | 不消费（一次到底） | 消费：G4/G5 在此转成 missingEvidence / 重组装 |

### 4.4 answerable 与 confidence 判定（确定性规则）

```text
answerable = 以下任一为真：
  a) Explicit 命中数 ≥1（02 Exact-Explicit 通道）
  b) 双通道共识候选 ≥2
  c) Structural 路由且图主路径返回了非空结果
confidence：
  high   = explicit 命中 + 共识候选 ≥3 + 无 graph_boundary
  medium = 有共识但无 explicit；或 spec-only 命中
  low    = 其余（单通道、fallback chunk 主导等）
```

判定结果的两个消费点：Fast 模式随包返回（agent 自行决定是否追问）；Deep 模式 **answerable=false 触发短路，不走 LLM**（04 §3，D-24）。

## 5. MissingEvidence 合同（A5）

结构化 code 类型表（吸收外部建议 + 对齐 02 的 G 表）：

| code | 触发场景 | 信号来源 |
|---|---|---|
| index_stale / indexing_pending | 索引落后于工作区 | 01 freshness / 05 同步状态 |
| graph_boundary | 调用链在动态分发/函数指针处断裂 | 02 图扩展截断 + unresolved_refs |
| symbol_ambiguous | inferred 符号多义（refreshUI vs refresh） | 02 Exact-Inferred 多命中 |
| unresolved_reference | 关联符号解析失败 | 01 unresolved_refs(status=failed) |
| stale_doc_reference | 命中文档引用了已删除符号 | 01 spec_references.stale（G4） |
| retrieval_truncated | 预算裁剪丢弃了 tier≤2 候选 | 本组件 truncated/omittedCount |
| no_context_match | 无共识候选 | 02 G3 二轮后仍空 |

每条 message 必须含"缺什么 + 为什么缺"；**可执行的自愈建议放 nextQueries**（从 top 候选符号/文件构造 2-3 条，确定性生成）。

## 6. Markdown 渲染（对外表现层）

Fast 模式 MCP 直接返回此渲染；04 的 prompt evidence 分节复用同一 formatter 的子函数。

```markdown
## Relevant Context

### Code
[E1] TokenService.refresh — src/auth/token_service.py:45-82
     reason: explicit symbol + BM25
     45 | def refresh(self, t):
     46 |     ...

### Flow
[F1] AuthMiddleware.verify → TokenService.refresh → TokenStore.rotate

### Docs
[E7] docs/auth.md > 认证 > Token Refresh（design）
     ⚠ 引用了已删除符号 LegacyToken.rotate，文档可能过时

### Missing Evidence
- [graph_boundary] 调用链在 Plugin.execute 动态 dispatch 处中断

### Meta
confidence: high | index: fresh (5 min ago) | budget: 7.2K/10K
```

渲染纪律：代码带行号（codegraph_node 模式【已验证】，agent 可直接对齐 Edit）；引用格式 [E*]/[F*] 与合同一致（04 citation 的锚点）。

## 7. 时序与性能

本组件全部内存操作（排序装填 + 渲染），<20ms，不在关键路径上。唯一 I/O 是 01 的 freshness 查询（<5ms）。
