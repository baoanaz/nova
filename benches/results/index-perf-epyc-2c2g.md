## 1. 结论

LangChain 零网络冷启动三轮中位数 **40.950s**，旧机为 **45.462s**，
耗时缩短 **9.92%**；CPU 累计时间中位数 **36.656s**，
比旧机 **44.965s** 缩短 **18.48%**。
本次应用路径有改善，未兑现早期文档中“CPU 翻倍、约 23 秒”的预测。

旧机约 90 Mbps 来自不同端点/工具，不能把比值当严格的带宽提升倍数。

## 4. 真实 API

恢复凭据后，独立运行 full，再运行 TTFB，期间没有并行启动本轮常规测试或构建。
full 使用全新索引，2986 文件、20931 chunks、零复用，`report.errors=[]`。

| 指标 | 新 VPS，单次 | 旧 Xeon 基线 |
|---|---:|---:|
| 墙钟 | 52.664s | 63.326s |
| 峰值 RSS | 843.3 MiB | 823.4 MiB |
| HTTP 请求 | 58，全部 200 | 历史原始记录 |
| 网络活跃窗口并集 | 15.142s | 29.750s |

单次墙钟缩短 **16.84%**。本次 CPU 累计 47.593s，计费输入 3,565,219 tokens，
响应体 238,806,124 B（227.743 MiB）；首请求到末响应窗口为 26.361s。
这是一次跨日期 API 样本，服务端负载、路由和本机缓存均可能影响结果，不是稳定提升承诺。

TTFB 探针每档 8 请求、每请求 500 个公共 chunk；三个档位全部 HTTP 200，
每档约 48.67 MiB 响应。速率单位为 MiB/s（历史字段名写作 MB_per_s）。

| 并发 | 墙钟 s | 聚合 MiB/s | TTFB 中位 s | 响应体传输中位 s |
|---|---:|---:|---:|---:|
| 1 | 7.50 | 6.49 | 0.538 | 0.374 |
| 4 | 2.52 | 19.30 | 0.855 | 0.278 |
| 8 | 1.67 | 29.10 | 0.948 | 0.299 |

探针的 TTFB 在收到响应头时记时，包含连接、服务端等待；响应体随后读完。
这些值用于观察 API 路径，不等于 VPS 端口速率，也不足以据此提高生产索引并发。
DeepSeek 经 zace 的实际 provider 完成一次最小文本请求；这验证凭据与协议，未覆盖完整 ask_project 流程。
