## 1. 已确认的方向

**多路检索负责发现，结构图负责连接，输出构建负责取舍。**

不以准确识别所有问题意图为前提。Agent 的问题开放且多样，服务内部不建立强制分类、依赖分类结果才能工作的 planner。通过工具描述限定优势区间，让 Agent 按所需交付物选择工具；即使选得不理想，工具仍尽力返回有用结果。

- `search_context`：功能和行为的实现查找，交付可操作的代码证据、相关连接和精确位置。
- `ask_project`：项目内部开放式询问，消费更宽的相关证据，用一次逻辑 LLM 调用交付综合解释、必要证据和缺口。
- 两个工具共享索引、召回与关系发现，不分叉成两套检索引擎。
- ask 不受 search 的 Agent 返回包裁剪限制，但仍受自己的模型输入、延迟和成本预算限制。
- 优化目标是减少完成正确任务所需的总上下文与调查成本，不是使每一次响应都尽可能短。

这里的“开放式询问”不是通用知识问答；回答仍必须以项目代码和文档为依据。符号、路径、行号是可直接利用的锚点，不是对整句问题进行意图分类的依据。

## 3. 各能力如何发挥优势

| 能力 | 独有贡献 | 必须保留的边界 |
|---|---|---|
| 符号 / 路径 / 字面量 | 明确对象、API、配置项、错误字符串和位置 | 模糊候选不得冒充精确命中；歧义应可见 |
| BM25 | 项目术语、协议字段、注释及文档的词法证据 | 文本提及不是调用关系 |
| Vector | 用户表达与不同命名的实现、文档之间的语义映射 | 相似度不是事实支持或图边证明 |
| 结构图 / 符号解析 | 跨文件连接、调用点、重导出、类型与绑定关系 | 不确定关系、动态调度和遍历截断应可见 |
| 文档 / 测试 | 设计意图、使用约束和边界案例 | 文档可能过期；静态关联测试不等于运行覆盖 |

例：“如何避免重试导致重复提交？”

1. Vector 找到幂等性、重放控制等语义相关实现。
2. BM25 / Literal 找到 `idempotency_key`、`request_id`、`retry` 和相关契约。
3. 符号索引定位请求入口、重试和去重实现。
4. 图发现入口、重试、请求 ID 与去重实现的连接及调用点。
5. 文档和测试提供幂等键过期、断网重试等边界。

不要求先将该问题准确分类；各能力贡献候选，再统一去重、排序、组织。search 返回关键实现与连接，ask 综合机制和局限。

### CodeGraph 能力的接入位置

- 索引阶段：参考统一抽取接口、语言适配器、跨文件解析与关系失效重解析。
- 证据发现阶段：围绕可信召回锚点补 callers / callees、有限桥接、框架绑定与候选测试。
- 组织阶段：关系边附调用点与来源，精确目标优先分配源码，超长函数围绕关键调用点选择窗口。
- 可信度阶段：明确动态边界、启发式关系、新鲜度未知与分析截断。

不是引入另一个大检索器后直接拼接其结果，也不要求 Agent 学习 CodeGraph 的多个底层工具。

## 4. 工具优势区间与描述草案

本节仅是后续契约变更的候选文案，当前工具描述未修改。

### search_context

> 查找实现某项功能、行为或处理逻辑的代码，返回关键实现片段、文件与行号，以及相关调用关系和必要文档。适合定位功能、追踪实现、调试取证和修改前查找代码。不生成综合性项目回答。已知文件请直接读取；需要精确标识符的全量引用请使用 grep。

### ask_project

> 根据项目代码与文档回答开放式问题，例如某个机制如何工作、多个模块如何协作、设计与实现是否一致。服务端综合相关证据，返回精简解释、关键引用和证据缺口。适合理解和比较，不以返回大量可直接编辑的源码为目标。

| Agent 想拿到什么 | 建议工具 | 示例 |
|---|---|---|
| 把实现找出来，自己判断和修改 | search | “找到请求超时后重试的实现” |
| 先解释清楚，再决定下一步 | ask | “超时、重试和取消如何协调，什么情况不会重试？” |

描述是引导，不是可靠路由保证。CodeGraph 的维护说明也提醒工具描述不能保证改变 Agent 选择；NOVA 应验证工具选择率，但不能将正确选择作为结果可用的前提。不要求先 search 再 ask，不新增用户必须掌握的底层 MCP 工具。

## 5. 共享 EvidenceSet 与分流输出

```text
问题
  ↓
共享索引与证据发现
符号 / Literal / BM25 / Vector / 图关系 / 文档测试关联
  ↓
候选去重、排序、关系组织、有界缺口补充
  ↓
EvidenceSet（内部集合，不等同 Agent 返回包）
  ├─ SearchPack 构建 → 精选源码 + 连接 + 位置 → Agent
  └─ AskEvidence 构建 → 更宽的去重证据 → 一次 LLM
                                      ↓
                        校验与 AnswerPack 渲染 → Agent
```

EvidenceSet 已在阶段 B 实现为请求内类型，见 [evidence.py](../../core/nova_core/contextpack/evidence.py)。第一版复用 Candidate、Store、Flow、索引信号与现有 ContextPack，不新增持久化表、图数据库或第二份完整源码。下列字段仍是后续增量设计候选，不能视为首版全部已实现。

建议内部记录：

- 项目、分支 / scope、符号与文件位置；
- 源码版本 / 内容哈希、解析器版本；
- 候选排名、召回原因、结构关系与调用点；
- 关系来源、解析状态、动态边界与截断状态；
- 可读取的源码范围、文档 / 测试身份；
- 新鲜度状态和未覆盖范围。

这些字段需在实施前与现有 schema 对齐；仅新增确实缺失的数据，不为概念完整而迁移所有表。

### 三种预算必须分开

| 预算 | 控制内容 | 原则 |
|---|---|---|
| 检索工作预算 | 候选数量、关系遍历、耗时和内存 | 有界工作，截断可见 |
| ask 模型输入预算 | 总结模型消费的证据与 prompt | 按模型上下文、注意力、延迟和成本限制 |
| Agent 返回预算 | search / ask 的最终响应 | 关注宿主内联限制与多轮上下文成本 |

ask 不受 SearchPack 裁剪限制，不意味着无限输入。第一阶段先解耦流程，保留现有预算作为回归基线；更宽输入的具体档位通过评测确定，不能凭直觉把上限翻倍。检索相关性决定装填量，上限不是必须填满的目标。

## 6. search：相关、互补、可操作的一组证据

按证据作用分节，不按 BM25 / Vector 等技术来源分节。

1. **核心实现**：关键符号、位置、必要源码、与问题的关系。
2. **相关连接**：必要入口、下游实现、重导出和绑定关系，附调用点与来源。
3. **约束与边界**：相关配置、类型、错误分支、测试或文档。
4. **覆盖限制与继续阅读**：歧义、未解析关系、截断范围、完整实现位置。

空节省略，不默认附整个模块，不使用总结 LLM。search 的自然语言说明来自可验证元数据或模板，避免另建自由推断层。

### 证据选择原则

- **直接相关性**：是否回答查找需求。
- **不可替代性**：移除后是否丢失关键实现、条件或连接。
- **信息增量**：是否只是重复包装层、同一源码区间或同一事实。

第一版用可观测的代理信号实现：精确目标、真实实现与包装层、路径桥接、重复区间、不同分支和关系来源。不是声称确定性算法能理解所有代码事实，也不在融合阶段随意改变现有 RRF 纪律。

关键保真规则：

- 精确命名的目标先得到实现预算，不让邻居先吃完预算。
- 合并相邻 / 重叠源码范围；辅助节点可只返回位置或签名。
- 大函数窗口围绕行号锚点、调用点和必要分支，不固定只取前 N 行。
- 窗口不得伪装完整函数；安全截取无法确定时保留完整实现或明确要求展开。
- 静态图路径不称为运行时轨迹；启发式边不得渲染为已确定调用。
- 测试用于边界和候选影响，不宣称执行过测试或证明测试集合充分。

展开优先提供现有 read 可用的位置。新增不透明展开 ID 或工具参数不是首版前提；确有必要时再经契约评审。

## 7. ask：一次 LLM 消化更宽的相关证据

### LLM 之前

从 EvidenceSet 单独构建 AskEvidence：

- 保留关键实现、连接、不同分支以及必要文档 / 测试；
- 去除重叠源码、重复模板和无关邻居；
- 保留足以判断行为的正文，不能只给签名要求模型解释机制；
- 显示关系来源、歧义、动态边界、新鲜度与截断；
- 允许有界定向补检，不增加 LLM planner 或审查调用。

模型输入不直接复用面向 Agent 的长 Markdown；可沿用共享源码 formatter，但组织为紧凑证据卡、关系表和已知缺口。

### 一次逻辑 LLM 调用

同一次调用完成：理解开放式问题、综合跨文件机制、区分实现与设计、选择必要证据、明确事实 / 推断 / 未知。

候选结构化输出包含 claims、evidence IDs、edge IDs、gaps 和状态。模型选择引用，服务端填入真实文件位置与原始源码，不让模型编行号或改写证明片段。具体输出 schema、协议支持和错误处理待评审；不是所有现有 provider 都保证严格结构化输出。

正常回答阶段最多一次逻辑调用。网络重试仍按现有传输策略单独记录，不承诺上游在超时场景绝不重复计费；不做第二次总结、规划、语义审查或自动格式修复调用。

### LLM 之后

确定性检查引用身份、关系来源、源码范围、版本和结构；无效输出采用部分回答或有依据的降级，不能删去引用后仍把对应 claim 当成已验证事实。

必须明确：**引用合法不等于结论语义正确**。语义支持率由离线评测核验，模型可能正确引用但错误解释。

默认返回：直接回答、关键机制、少量必要证据与精确引用、缺口与不确定性。不再附完整 SearchPack。

### 部分回答与失败

考虑后续区分 sufficient / partial / insufficient：有可信局部证据时允许有边界的部分回答；几乎无依据时零 LLM 调用。该变化需评审现有 `answerable=false` 短路和 response status，不在首版默默改变。

一次 LLM 在读完证据后发现缺口，无法在同一次普通总结调用内补搜并继续综合，应如实返回缺口。未配置 / 失败降级仍保留可用证据和原因，但采用有界输出，不默认泄露整个内部集合。

## 8. 结构索引、同步与多项目

### 结构索引

参考 CodeGraph 的“统一抽取底座 + 语言适配 + 跨文件 resolver + 框架适配”分层，不照搬 TypeScript / Rust kernel 双栈。

语言验收分别衡量：结构切片、定义定位、跨文件解析、调用边、框架绑定。建议先补 TS/JS，再按目标仓库分布选择 Rust/Go、Java；不同时承诺全部语言。

边保留解析依据、调用点与不确定性。框架规则与启发式动态边按独立适配器管理，新增规则需正例、同名误连反例、删除 / 改名 / 重导出失效测试。动态边界报告优先于凭弱线索硬补边。

### 同步与新鲜度

现有预热保留。后续参考启动补偿、后台监听和查询贡献文件检查三层机制。

CodeGraph 可以直接读本地文件；NOVA 的远端服务不能照搬其读盘校验。应由客户端变化清单 / 内容版本与服务端索引版本协作；在无法核验时报告 unknown，不将 checkpoint 冒充不可变快照。

Watcher 与原增量同步共享协调器，变更风暴合并，资源耗尽和失败降级可见，不为每个 MCP 进程重复创建无界监听。不改变既定符号链接与忽略规则边界。

### 多项目 ask

后续各项目检索后由 service 校验权限，建立统一引用命名空间、来源与总预算，再调用一次 LLM。不能每项目一次总结；不能把同名符号当跨项目真实调用。部分项目失败报告覆盖缺口，保留当前降级行为直到新链路验收。

跨调用源码省略暂不启用：MCP 连接不等于 Agent 的持久上下文，子代理和上下文压缩可能丢失已返回代码。

## 9. 后续实施顺序与交付门槛

| 阶段 | 交付内容 | 验收与边界 |
|---|---|---|
| A：基线与契约评审 | 固定 search / ask 用例、预算、延迟、正确性；审议内部结构与描述 | 零功能改动；记录既有失败和新设计冲突 |
| B：证据集合分流 | 在共享检索上分离 EvidenceSet、SearchPack、AskEvidence | 保持现有预算和失败语义；ask 不经 SearchPack 裁剪；不增加 LLM 次数 |
| C：search 证据选择 | 精确目标优先、区间去重、相关连接、调用点窗口和章节 | 不丢必需实现；短响应不得增加总调查成本 |
| D：ask 证据综合 | 紧凑模型输入、证据选择与引用、精简 AnswerPack | 一次逻辑 LLM；测语义支持而不只查引用存在 |
| E：结构质量 | 强化既有语言、TS/JS；有限桥接、框架和动态边界 | 图边准确性、歧义、增量失效专项；可与 C/D 并行 |
| F：一致性与工作区 | Watcher、多项目统一总结、版本协议 | 权限、来源、变更风暴、部分失败、跨进程和资源上限 |

B 是优先实施入口；E 不应阻塞分流和 ask 改善。每阶段独立可回滚，不夹带重构、格式化、全栈替换或 embedding 模型迁移。

### 质量与成本指标

- 定义定位与关系边 precision / recall，尤其同名误连和动态边伪确定。
- 完成任务所需的实现 / 连接证据覆盖率，以人工标注基线核验。
- ask 重要结论语义支持率、错误断言率、引用合法率分别统计。
- Agent 达到正确结果的总工具调用、补搜 / 补读、累计 token 和耗时。
- search / ask P50 / P95，ask 模型输入 / 输出 / usage 和重试次数。
- 源码窗口保真、截断可见性、新鲜度 unknown / stale 处理。
- 多项目权限、引用身份与版本混杂错误。

固定模型、仓库版本、问题与预算做消融：现有基线 → 分流 → 选择器 → 结构增强 → ask 输出。不要一次引入所有组件后归因收益。需要付费模型或真实 embedding 的基准另行确认，不自动执行。

必测场景：自然语言与符号混合、中英问题、同名定义、重导出、超长函数、关键分支在尾部、图不连通、文档冲突、索引过期、模型失败 / 格式错误、混合工作区部分失败。工具描述需测选择率，但不能通过只给理想输入证明可用。
