# 向量阶段多窗口并行（TASK-115）实测报告

> 设备：`vps-la-2c2g`（2 vCPU / 1.9 GiB / 洛杉矶）｜embedding：`voyage-4-lite` @1024（API，`EMBED_CONCURRENCY=4`）
> 日期：2026-09-26｜分支：`feature/task-115_embed-parallel0926`｜输入：`index-perf-task114-vps.md`（TASK-114 的账）
> 原始计量 JSON：`raw/task115/`（含一次失败的对照设计，保留作负结果）

## 0. 一句话结论

**langchain 真实 API 冷启动 79.5s → 63.3s（-20%）；HelloAgents 17.2s → 16.0s（-7%）；峰值 RSS +75MB（748→823MB）。**
换算法（把窗口按 K 切小）**没有任何收益**（74.7s vs 74.0s）——原因与结论见 §2，这是本卡最有价值的发现。

## 1. 设计：窗口在 pipeline 层"攒满再派发"

TASK-114 的结构是"1 生产者 + 1 消费者"，消费者内部 ``取回 → 解码 → 落库`` 串成一根链
（langchain 里它一户占 48s，链路在解码/落库期间空转）。TASK-115 改成：

```text
主线程（生产者）      解析/切分 → SQLite/FTS → 攒窗（满 2000 chunk 就派发）──▶ 有界队列(K+2 窗)
                                                                              │
消费者 #1（EmbeddingSink）  ◀─────────────────────────────────────────────────┤  取回(4 路) → 解码 → LanceDB upsert → 缓存
消费者 #2（EmbeddingSink）  ◀─────────────────────────────────────────────────┘  同上，与 #1 重叠
```

- `ZACE_EMBED_WORKERS`（默认 **2**，夹在 1..4；设 1 即退回 TASK-114 行为）；
- 窗口 = `批大小 × 并发`（这里 2000）**保持不变**，由主线程攒满整窗再派发；
- 队列有界（`K+2` 窗）→ 背压即内存护栏；峰值向量 ≈ `K × 窗口 × 33KB`；
- 失败/关停语义与 TASK-114 一致（异常回抛主线程、abort 丢弃缓冲、关停派发尾窗 + flush）。

## 2. 关键发现：窗口不能按 K 切（负结果留档）

第一版实现让**每个消费者各自攒窗**（窗口 = `2000 ÷ K`），结果：

| 设计 | K=1 | K=2 | 说明 |
|---|---|---|---|
| 每消费者切窗（`2000/K`） | 74.73s | **73.98s** | 等于没并行 |
| ★ 全局攒满再派发（本卡定稿） | 79.49s | **63.33s** | -20% |

原因：provider 的并发是**单次 `embed()` 调用内**的（`batch_size=500` × `concurrency=4`）。
窗口切半后，每次调用只剩 2 个批 → 单调用只能用 2 路并发；两个消费者加起来仍是 4 路，
与 K=1 完全相同。**"想要更多请求在飞"，必须让每次调用仍持有整窗（4 批）再把整窗分给不同消费者。**

> 口径提醒：K=1 在两次设计里分别是 74.73 / 79.49s（机器与链路 ±6% 抖动）。两组 A/B 都是**同会话背靠背**跑的，
> 所以组内差值可信；跨组绝对值不可直接比。

## 3. 实测（同会话背靠背）

### 3.1 零网络替身（local-only，免费）

| 配置 | 墙钟 | 峰值 RSS |
|---|---|---|
| K=1 | 44.6s | 699.5MB |
| K=2（默认） | 45.5s | 777.2MB |
| K=3（切窗设计下的对照） | 44.3s | 741.0MB |

local-only 全是 CPU（无 I/O 可重叠），K=2 略慢 0.9s、多 78MB——**符合预期，不构成回归**；
它同时也说明"多消费者"的收益来自 I/O 与 CPU 的重叠，而不是 CPU 变快。

### 3.2 真实 API（langchain @ `e75dae1f`，3.56M token/次）

| 指标 | K=1 | K=2 | 变化 |
|---|---|---|---|
| 墙钟 | 79.49s | **63.33s** | **-20%** |
| 网络在飞并集 | 37.67s | 29.75s | -21% |
| 有效吞吐 | 6.03 MB/s | **7.69 MB/s** | +28% |
| 首个请求→最后请求结束 | 51.52s | **34.01s** | -34% |
| 生产者被背压等待 | 29.33s | 15.13s | -48% |
| 峰值 RSS | 748.4MB | 823.4MB | +75MB |
| CPU 累计 | 54.9s | 55.4s | ≈ |
| 请求数 / 下行 | 57 / 227.2MB | 58 / 228.6MB | ≈ |

### 3.3 真实 API（HelloAgents @ `93e77ea`，中等仓库：2729 chunk ≈ 1.4 窗）

| 配置 | 墙钟 | 峰值 RSS |
|---|---|---|
| K=1 | 17.21s | 501.9MB |
| K=2 | **15.98s（-7%）** | 541.8MB |

中等仓库只够一个有意义的窗 + 一个尾窗，收益自然小于 langchain——但**没有退化**
（若窗口按 K 切小，这种规模两个消费者都填不满、只能等关停串行 flush，会更慢）。

## 4. 剩余瓶颈与调参建议（给新 VPS）

当前（K=2）剩余结构：消费者每个窗口仍是 `取回 → 解码 → 落库` 串行，两个消费者只能覆盖一部分
链路空转；墙钟 63.3s 里网络并集 29.7s / 生产者本地 18.4s / 两个消费者的 CPU 部分合计 ~33s。

按 2 vCPU + 200Mbps 的新机外推（单核 ~2×，TPM 地板 3.56M ÷ 16M = **13.7s**）：

| 项 | 现状 | 新机估计 |
|---|---|---|
| 生产者本地 CPU | 18.4s | ~10s |
| 消费者（每窗 取回+解码+落库） | ~33s/消费者 | ~18s |
| 网络下限 | 29.7s 在飞 | max(13.7 TPM, 227MB÷25MB/s≈9s) ≈ **14s** |
| **墙钟** | 63.3s | **~22–28s** |

上机后可调的旋钮（按性价比）：

1. `ZACE_EMBED_WORKERS`：先 2；内存 ≥4GB 时可试 3–4（本机 2 核 + 1.9GB 不宜）；
2. `EMBED_CONCURRENCY`：内存够时可以升到 8（窗口随之变 4000 chunk，峰值向量 ≈ K×132MB）——
   这会同时增加"每次调用内的批数"，是**继 K 之后下一个能继续压低网络窗口的旋钮**；
3. 再往下要动 provider 内部（取回与解码分离 / 流式），本卡明确不做。

## 6. 本轮不做

- provider 内部改造（async/流式取回、取回与解码分离）；
- 多进程（P2-6，2 核收益不确定）；
- 不改冻结契约、检索链、SQLite 单写者不变量；不做质量参数调整。
