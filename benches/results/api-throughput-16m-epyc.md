## 结论

- 纯 API 传输在 batch=500、并发=16/32 时分别达到 283.045/292.426 Mbps。
  32 相比 16 只增加约 3.3%；没有测到 1 Gbps。
- 按实际 usage 控制 16M TPM，运行约 66 秒，实际完成 15.704M TPM、99.754 Mbps，
  129 请求全部 HTTP 200。该样本的理论 16M TPM 响应速率约 101.635 Mbps。
- 同样的 2986 文件 / 20931 chunks，完整索引并发 4 为 48.091s；并发 8 为 54.126s，
  RSS 从 864.3 升至 1068.0 MiB。本轮不支持提高这台 2 GiB VPS 的生产索引并发。
- 原配置完整索引平均使用 0.979 个 CPU 核心，即双核总能力的 49.0%。
  本地计算、入库与流水线调度占据明显成本，双核没有持续满载。
- OVH 8 连接独立下载未完成，补测返回 HTTP 429，已停止，16 连接未执行。
  不能把 API 的约 300 Mbps 平台断言为 VPS 的物理端口上限。

## 1. 16M TPM 与 Mbps 的关系

Voyage [官方限流说明](https://docs.voyageai.com/docs/rate-limits) 当前列出
`voyage-4-lite` 的基础额度 16M TPM / 2000 RPM；项目可设置更低额度。
本轮成功响应没有返回可用的 quota 响应头，没有核实该 Key 的实际账户 tier；
16M 是本轮采用的客户端节奏目标，不是通过压测推断出的账户硬上限。

固定 1024 维 JSON float 输出时，每条文本通常产生约一条固定大小的向量，
而输入 token 数取决于文本长度。因此：

```text
持续响应 Mbps = TPM / 60 × 平均响应字节/token × 8 / 1,000,000
```

| 输入组成 | 响应字节/token | 16M TPM 对应响应速率 |
|---|---:|---:|
| 本轮完整 LangChain 索引 | 66.982 | 142.895 Mbps |
| 本轮传输测试的固定随机样本 | 约 47.642 | 约 101.635 Mbps |

按完整索引的输入组成，要持续产生 1 Gbps 的响应体需要约 **111.97M TPM**。
提高并发能减少等待、提高短时吞吐，但不会增加 16M TPM 下每分钟允许处理的输入 token 数。
不能为了让带宽表盘更高而任意切碎 chunk 或增大维度；这些变更会影响索引规模与检索行为。

## 2. 纯传输实验

使用 `tpm_probe.py`，同一组固定随机样本：从既有 `chunk_texts_for` 提取的 23648 条文本中
选取 16000 条，seed=20261007，每条最多 32000 UTF-8 字节。
该提取工具与完整 ingest 的过滤/去重路径不同，**不是完整索引的 20931 chunks 集合**。
各配置使用同一组文本；每档 API 实际返回 4,281,759 tokens。

模型 `voyage-4-lite`，input_type=document，1024 维、JSON float；直连，不使用代理。
共享连接池，流式读完响应并丢弃向量正文，只从尾部取 usage；不做完整 JSON 解码或入库。
下面是单轮短时样本，速率按成功响应实体正文的字节 / 整段墙钟计算，含连接与服务器等待。
原始扫描未逐条保留 Content-Encoding，不能把这些数值声称为网卡线速。
随后对 500 条测试文本分别使用默认和 identity 编码请求：两次均返回 identity，
实体正文、HTTP 传输正文及 Content-Length 都为 6,389,382 B；它只核验了这两次响应。
当前探针已补记 content_encoding 与 wire_body_mbps，区分压缩后的 HTTP 正文字节；仍不包含 TCP/TLS 开销。

| batch | 并发 | 请求数 | 墙钟 s | 响应 Mbps | 外推 M TPM | 平均 CPU 核数 |
|---:|---:|---:|---:|---:|---:|---:|
| 500 | 4 | 32 | 9.306 | 175.487 | 27.608 | 0.235 |
| 500 | 8 | 32 | 7.123 | 229.266 | 36.068 | 0.388 |
| 500 | 16 | 32 | 5.769 | 283.045 | 44.529 | 0.535 |
| 500 | 32 | 32 | 5.584 | 292.426 | 46.005 | 0.571 |
| 1000 | 16 | 16 | 5.848 | 279.234 | 43.930 | 0.402 |

所有请求 HTTP 200。短时外推 M TPM 不能当持续分钟吞吐；各档之间根据已测 token 数等待额度窗口，
不是持续向服务器发送 46M TPM。并发 32 一档只有一波 32 请求，不能据此宣称长期稳定速率。

随后清空本轮请求时间窗口，用首轮逐批实际 usage 校准发送节奏，目标 16M TPM、65 秒发送窗口。

| 指标 | 实测 |
|---|---:|
| 包含尾部请求完成的墙钟 | 65.993s |
| 实际 tokens | 17,272,403 |
| 成功请求 | 129 / 129 |
| 完成速率，含启动/收尾 | 15.704M TPM |
| 实际发送记录的最大 60 秒 token 数 | 16,005,161 |
| 响应速率 | 99.754 Mbps |
| 平均 CPU 核数 | 0.127 |
| 峰值 RSS | 553.2 MiB |
| 实际最大在途请求 | 3 |

并发上限虽为 16，但节奏控制下实际最多 3 路在途。该样本达到 16M TPM 附近不需要持续占满 16 路。
发送记录的 60 秒窗口约 16.005M，线程调度边界造成约 +0.032% 的偏差；
本探针是接近 16M 的实验节奏，不是严格保证所有窗口不超额的生产限流器。
15.704M 的完成速率包含启动和末批收尾，不应解读为服务端达不到 16M。
真正持续控制 TPM 需要 token 计账和节奏控制；当前应用的并发参数本身不是 TPM 限速器。
重复使用同一组文本可能受服务端缓存影响，未做缓存隔离或证明其存在。

## 3. 完整索引对照

两轮依次运行，独立索引；无本轮构建、安装或常规测试与其并行。
cgroup：MemoryHigh=1200M / MemoryMax=1500M / MemorySwapMax=512M。
主机既有业务服务未停止，文件缓存未清空；仅各一轮，不把差值当稳定性能承诺。

| 参数/指标 | 并发 4 | 并发 8 |
|---|---:|---:|
| batch / K / 维度 | 500 / 2 / 1024 | 500 / 2 / 1024 |
| batch token budget 配置 | 300000 | 300000 |
| 墙钟 s | 48.091 | 54.126 |
| CPU 核秒 | 47.090 | 49.329 |
| 双核总利用率 | 49.0% | 45.6% |
| 峰值 RSS MiB | 864.3 | 1068.0 |
| 实际 tokens | 3,565,219 | 3,564,989 |
| HTTP 请求 | 58，全部 200 | 57，全部 200 |

并发 8 在本轮耗时多 12.55%、RSS 多 23.57%，API 窗口虽缩短约 2 秒，整任务没有因此更快。
之前同配置 C=4 也测过 52.664s，说明主机/缓存/服务端状态会产生波动；本轮证据支持保留 C=4，
不支持把单次数字包装成已经找到全局最优配置。

### 时间组成

以本轮 C=4 为例，**48.091s 墙钟**与 **47.090 核秒 CPU**是不同单位：
CPU 时间是进程所有线程用户态和系统态计算时间之和，折合约 0.979 个核心，
不能说“墙钟时间的 98% 必然是 CPU 阻塞”，也不能再把它与网络时间相加。

以下是探针的累计墙钟分项，可能重叠或嵌套，不能相加成一个饼图：

| 阶段 | 累计墙钟 s | 解释 |
|---|---:|---|
| SQLite 文件应用 | 9.421 | 含 FTS 写入 5.711s，其中 jieba 分词 4.983s |
| JSON 响应解码 | 7.381 | 本地把 API 响应变为 Python 数据 |
| LanceDB upsert | 7.230 | 向量入库，含存储库内部等待 |
| tree-sitter 解析 | 4.637 | 本地源码解析 |
| 图关系解析 | 3.773 | 本地关系整理 |
| 扫描规划 | 1.459 | 本地文件扫描/规划 |
| 至少一个 HTTP 请求在途 | 16.370 | 含服务端等待、传输及客户端调度，与以上工作重叠 |

C=4 的整体处理速度约 4.448M TPM，显著低于纯传输测试的能力。
此前零网络本地路径中位数已是 40.950s；真实 JSON 解码与浮点数据处理还会增加成本。
本地替身使用零向量、绕过真实网络响应解析，不是“把线路变成无限带宽”的精确等价实验。
目前不能仅靠拉高并发或网卡速率推导完整索引的线性加速。

### 当前配置建议

这台 2 GiB VPS 的完整索引保持已测原配置：

```dotenv
EMBED_BATCH_SIZE=500
EMBED_CONCURRENCY=4
EMBED_BATCH_TOKEN_BUDGET=300000
ZACE_EMBED_WORKERS=2
EMBED_DIM=1024
```

若单独测量 API 路径的短时响应吞吐，batch=500、concurrency=16 已接近本轮平台；
concurrency=32 的增益很小，不代表完整索引也应该设成 16 或 32。

实现约束：`EmbeddingPipeline` 窗口为 `min(batch_size × concurrency, 4000)`，
另有 K 个消费者；并发配置不等于持续实际 HTTP 请求数。
当前 Voyage 配置没有 tokenizer，批次预算走 UTF-8 字节上界，300000 并不意味着每请求 300000 个真实 tokens。
本轮 C=4 平均约 61469 tokens/请求。
官方当前 [API 文档](https://docs.voyageai.com/reference/embeddings-api) 允许 lite 每批最多
1000 条/1M tokens，但仓库传输配置仍限制预算到 320000；不能直接把配置改为 1M 而忽略实现约束。
本轮没有修改生产参数或业务代码。

## 4. 复现与计账

```bash
set -a; source .env; set +a
HF_HUB_OFFLINE=1 .venv/bin/python benches/embed-bench/tpm_probe.py \
  --repo ../benchmark/langchain --paced-seconds 65 \
  --out .local/bench/<新目录>/transport.json
```

探针会消耗真实 API 配额，不做自动重试；失败会记录并停止下一档测试。
本次传输扫描+持续测试实际消耗 38,681,198 tokens；两轮完整索引消耗 7,130,208 tokens，
编码校验另消耗 17,560 tokens，合计 **45,828,966 tokens**。
完整索引需从配置加载后按单进程环境覆盖 EMBED_CONCURRENCY=4/8，再调用 coldstart_probe，
使用上述内存护栏和全新 --data 路径。不要用强制固定 C=4 的 benchmark-vps.sh 做此参数对比。

OVH 公共文件的 8 连接测试首次只记录 RuntimeError；补测捕获 HTTP 429，均未产生可用聚合成绩，
也未继续 16 连接。它与 API 的成功请求分开记录；没有回避限流或用错误响应计算吞吐。
