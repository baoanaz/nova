## 0. 组件拆分总览（先回答两个问题）

### 0.1 拆分：四个物理单元，五层逻辑视图

```text
【逻辑视图】                      【物理单元（部署/发版物）】

Coding Harness
Codex / Claude / Cursor
        │ MCP stdio
        ▼
┌─ nova-client ──────────────────┐   ② nova-client
│  MCP 适配模块（协议壳）          │      Rust 单二进制，npm 分发
│  同步客户端（scan/hash/upload）  │      = Module/05 全部设计
│  CLI（login/sync/status/mcp）   │      不依赖 core，只说 HTTP 协议
└──────────┬─────────────────────┘
           │ HTTPS + Bearer token
           ▼
┌─ nova-service ─────────────────┐   ③ nova-service
│  HTTP API / Auth / User        │      服务化外壳（本文 §2-3）
│  Project / 租户隔离 / 索引 job   │      依赖 core，不含任何检索逻辑
│  审计 / 可观测                  │
└──────────┬─────────────────────┘
           │ 进程内调用（非 RPC）
           ▼
┌─ nova-core ────────────────────┐   ① nova-core
│  切片存储 / 检索 / 组装 / LLM    │      引擎纯库 = Module/01-04
│  （01 → 02 → 03 → 04）          │      零网络、零鉴权、零用户概念
└────────────────────────────────┘
                                    ④ nova-web
        ▲                            SPA，消费 service 的 REST API
        └───── nova-web ────────────  = Module/07
```

**依赖方向（单向，CI 强制）**：web, client → service → core；core 不依赖任何上层。

**对两个常见误解的澄清**：
1. **鉴权、用户注册、租户隔离、HTTPS 是 nova-service 外壳的职责**，不是 client 的——client 只保存/携带 token（Module/05 §7），不实现任何鉴权逻辑。
2. **MCP 不是独立部署单元**——它是 nova-client 进程内的协议模块（notace 单二进制模式【已验证】），拆成独立组件会造成分发/版本同步的额外复杂度而无收益。

### 0.2 为什么 core/service 必须分离（本文最重要的一段）

外部建议把 server 当一整块。拆开的收益：

| 部署形态 | 组合方式 | 分离后如何实现 |
|---|---|---|
| **A. 云端 VPS**（V1 主形态） | service(HTTPS) + core + web + client(远端) | service 把 HTTP/鉴权/租户映射到 core 的 project 级调用 |
| **B. 本地单机**（V2，隐私/离线诉求） | client 直嵌 core，进程内调用，无 HTTP 无多用户 | core 是纯库，client 换一个"本地模式"分支即可复用全部引擎能力 |
| **C. 公司内网** | 同 A，改 base_url | 部署只是配置（外部建议的原则，落地为 D-34/D-38） |

如果不分离（引擎逻辑写进 HTTP handler 里），形态 B 永远做不了——这正是 GitNexus/ragcode 全本地项目与 notace 纯远端项目各占一半、谁也没法互相转化的结构性原因。

## 1. nova-core：纯库化边界（D-34）

**core 拥有**（Module/01-04 全部）：切片/索引/图/检索/组装/AnswerProvider；project 级数据目录（D-03）；索引配置与增量（D-07）。

**core 对 service 暴露的唯一接口面**（伪代码，实现语言无关）：

```python
class ContextEngine:                      # 进程内对象，per service 进程
    def resolve_project(identity_key) -> Project          # 或创建
    def ingest(project_id, changes: ChangeSet) -> JobId    # 01 §4.3，异步 job
    def sync_status(project_id) -> SyncStatus
    def search(project_id, query, max_tokens) -> ContextPack   # 02+03
    def ask(project_id, question) -> AskResult                 # +04
    def delete_project(project_id)                            # 级联删除
```

**纯库纪律（写进 CI）**：core 的依赖清单禁止出现 HTTP 框架/用户体系/租户概念；输入是 ChangeSet 与查询，输出是 ContextPack/AskResult；**core 的字典里没有 "user"，只有 "project"**——多租户是 service 把 user 映射到授权 project 集合的问题（§2.3）。

## 2. nova-service：服务化外壳

### 2.1 REST API 面（D-37，client 与 web 的共同合同）

```text
Auth（web 用 session cookie；client 用 Bearer token，双通道）
  POST   /api/auth/register          可配置关闭（环境变量）
  POST   /api/auth/login/logout      → session（web）
  POST   /api/auth/tokens            创建 API token（前缀明文仅此一次返回）
  GET    /api/auth/tokens            列表
  DELETE /api/auth/tokens/:id        revoke

Project
  POST   /api/projects/resolve       {identityKey, displayName} → {projectId, created}
                                     （Module/05 §3.4 的服务端侧；幂等）
  GET    /api/projects               我的项目列表
  GET    /api/projects/:id           index/sync 状态 + 统计（web 详情页）
  DELETE /api/projects/:id           级联删除（§3.1）

Sync（Bearer；client 专用）
  POST   /api/sync/batch-upload      {projectId, blobs[], branch, commit}
                                     → {accepted[], skipped[]}   按 blobHash 幂等
  POST   /api/sync/checkpoint        {projectId, blobHashes[]} → {checkpointId}
  POST   /api/sync/deletions         {projectId, paths[]}       按 (projectId,path) 幂等
  GET    /api/sync/status/:projectId

Query（Bearer；client 转发）
  POST   /api/query/search           {projectId, checkpointId, query, maxTokens}
                                     → {markdown, meta}   渲染在服务端（D-21，Module/05 §5）
  POST   /api/query/ask              {projectId, checkpointId, question}
                                     → {answer, evidenceSummary, meta}

Ops
  GET    /healthz                    存活+依赖检查
  GET    /api/usage/projects/:id     查询审计（04 §8 存档的读取口）
```

幂等语义在此明确（回应 Module/05 §9-3）：batch-upload 重复上传同 blobHash 直接返回 accepted；deletions 重复删除返回成功。

### 2.2 鉴权（D-39a）

- **API token**（client）：`nova_` 前缀随机串，库存 sha256 hash，明文仅创建时返回一次；revoke 即失效（软删）。
- **Session**（web）：登录签发 httpOnly cookie（signed session id 存库）；register 默认关闭（自部署单人场景默认够用，Task.md §14 可配置）。
- 密码 argon2id；所有 401/403 响应不区分"token 无效"与"无权限"细节（不给探测面）。

### 2.3 租户隔离双层模型（D-36）

```text
service 层（逻辑授权）：token → user → owns project?
  每个请求强制校验 projectId 归属；无 org 概念（表留 org_id 列，V1 恒 NULL，V2 预留）
core 层（物理隔离）：project_id → ~/.nova/projects/{id}/（D-03 目录树）
  删除 = rm -rf；备份 = tar；故障域 = 单项目
```

两层缺一不可：只有逻辑层 → SQL 漏写 WHERE 即泄露（GitNexus 单 token 教训，Background/04 §8）；只有物理层 → 无法表达共享/撤销。【权衡：双层是 Task.md §14"数据隔离不要后补"的最小完整实现】

### 2.4 索引 job 与可观测

- 索引 job：进程内 worker 池 + `project_index_jobs` 表（status/progress/error）——**每 project 串行、跨 project 并行**（01 §4.3 已定）。V1 不引入 Redis/消息队列（Task.md §18"不因未来可能需要引入分布式组件"）。
- 审计：04 §8 的查询审计存档归 service 管理入库。
- 可观测：结构化 JSON 日志（stderr/文件，含 requestId；secret 脱敏纪律同 05 §7）、/healthz、进程内存/索引队列深度等基础指标。

## 3. 数据安全落地（Task.md §15 兑现清单）

| 要求 | 落地 |
|---|---|
| 删除链路 | DELETE /api/projects/:id → core.delete_project → rm -rf 项目目录（blobs+index.db+vectors）+ 元数据行删除；审计留痕（不含内容） |
| TLS | 反代（Caddy 自动 TLS）终结，service 内网明文 |
| secret | 全部环境变量注入；token/hash 不进日志（01/05 纪律统一到 service） |
| 备份 | 数据目录 tar + 元数据库 dump 的 cron 脚本（V1 手册级，不做自动备份系统） |
| LLM 边界 | 默认配置下代码只到 VPS；启用外部 ANSWER_* 时**证据片段会发往该 LLM 提供商**——文档与设置页必须明示（Task.md"用户明确知道哪些代码离开本地"） |
| 保留策略 | 项目删除即全删（无软删除期，V1 从简，用户预期明确） |

## 4. 部署形态（D-38）

### A. VPS（V1 主形态）：docker compose 单栈

```yaml
services:
  caddy:        # 443 自动 TLS → service:8000(/api)、web:3000(/)
  nova-service: # volume: ~/.nova（projects/ + nova-meta.db）
  nova-web:     # 静态 SPA
```

- 规格：2C4G 起步（GitNexus 单容器 2GB 跑得动同类负载【快照参考】）；4C8G 舒适；磁盘按 Module/01 §3.4 估算（<500MB/百万行代码）
- 不上 k8s/微服务：单 VPS 单 compose 是 Task.md §18 与 Background/05 §7 的共识结论

### B. 本地单机（V2）：client 直嵌 core

nova-client 编译期带 feature 开关嵌入 core（进程内调用），MCP 工具行为不变、无鉴权无 HTTP——**core 纯库边界（D-34）保证这条路径今天设计、明天可做**。多用户/审计/playground 等 service 能力不在此形态承诺。

### C. 内网自部署

同 A，仅改 base_url；register 关闭 + 单管理员 token 模式。

## 5. 仓库组织（D-35）：monorepo，不拆 git

```text
nova/                        # 单 git 仓库
├── core/                    # ① nova-core（纯库；语言见 §6）
│   ├── chunking/  storage/  #    Module/01
│   ├── retrieval/           #    Module/02
│   ├── contextpack/         #    Module/03
│   └── llm/                 #    Module/04（llm 为 core 内模块，不独立成包）
├── service/                 # ③ nova-service（本文 §2-3）
├── client/                  # ② nova-client（Rust；含 mcp/ 模块）
├── web/                     # ④ nova-web
├── docs/                    # 设计文档（others/research 迁入）
└── benches/                 # golden set（02 §7-1）+ 跨组件契约测试
```

| 维度 | monorepo（推荐） | 多 git 仓库 |
|---|---|---|
| 跨组件协议改动 | 一次 PR 同步改 client+service+契约测试 | 三仓 PR 协调，版本号对齐成本高 |
| CI 依赖方向强制 | 单仓一条 CI 规则（core 禁 import 上层） | 各仓各自声明，容易漂移 |
| 参考项目实践 | ragcode/gitnexus/codegraph/notace 全是 monorepo | — |
| 未来要拆 | git filter-repo/subtree split 随时可拆，历史保留 | — |
| client 独立发 npm | monorepo 一样发（codegraph/notace 先例） | — |

**边界强制手段**：包依赖检查进 CI（core 的依赖清单出现 HTTP/用户体系即 fail）； benches/ 放跨组件契约测试（API schema 漂移即 fail）。

## 6. runtime 选型（D-39，已拍板：P1）

| 方案 | 组成 | 优势 | 代价 |
|---|---|---|---|
| **P1（推荐 V1）** | core+service = Python（FastAPI + sqlite3 + lancedb + tree-sitter-py + jieba）；client = Rust；web = SPA | 引擎迭代最快（检索策略/rerank/golden set 调优是 V1 主战场，Python 生态全齐）；ragcode 已验证同构技术栈【已验证】；client 已定 Rust（Module/05 §6） | 两个语言栈；V2 本地嵌入形态需重分发（PyInstaller/内嵌解释器） |
| P2 | 全 Rust（core+service 用 axum + rusqlite + lancedb + tree-sitter-rs；codegraph kernel 路线） | 单语言单二进制，性能上限高，形态 B 分发优雅 | 检索策略迭代慢（rerank 调优/golden set 循环在 Rust 里摩擦大）；V1 交付周期风险 |

推荐 P1 的核心理由：**V1 的胜负手是检索质量不是性能**（Fast 0.5s vs 0.2s 用户无感，检索不准用户直接流失）；D-34 纯库边界已保住 V2 性能瓶颈时把 core 换 Rust 的可能性（接口不变、实现替换）。

## 7. 开发优先级（吸收外部建议，与 Background/06 §6 落地顺序合并）

```text
1. nova-core     ★★★★★  先证明"比 agent 自己 grep/read 更快更准"（最小闭环 → 四通道 → 图 → C/C++）
2. nova-service   ★★★   core 稳定后包壳（API+鉴权+租户）；期间可用 core 的 CLI 直测引擎
3. nova-client    ★★★   与 service 并行（协议合同 §2.1 已冻结即可开工）；notace 蓝本
4. nova-web       ★     service 好后一周内出管理面（Module/07 范围）
```

## 8. V1 明确不做

| 不做 | 理由 | 何时 |
|---|---|---|
| Organization/团队 | V1 单人多项目；表结构已留 org_id | 真实多用户诉求出现 |
| Redis/消息队列/对象存储 | 单 VPS 进程内 worker 够（§2.4） | 多机部署时 |
| 自动备份系统 | cron+手册 | — |
| 项目软删除/回收站 | 从简，删除语义清晰 | 合规诉求 |
| k8s/helm | 单 compose 是 V1 上限 | — |
| 速率限制 | 单人/小团队自部署场景暂无恶意流量面 | hosted 服务化前必做 |

## 9. 开放问题

1. **runtime 终审**（§6 P1/P2）——影响 core 首行代码，建议评审会第一个拍。
2. **API 版本策略**：/api/v1 前缀与否——client 与 service 同仓同步发版，V1 可以不版本化，公开 API 化时再加。
3. **web 是否独立仓**：若未来 UI 交给独立迭代，monorepo subtree split 即可，V1 不预留。
4. **本地形态 B 的 client 二进制尺寸**：嵌入 core（Python）时 PyInstaller 打包 ~80MB，可接受性待 V2 评估。
