# 冷启动架构优化：真实客户端离线回放

2026-10-07，EPYC 7282 / 2 vCPU / 1919 MiB RAM。代码为当前未提交工作区，未部署。

## 结论与边界

真实 Rust MCP 客户端的首次同步加查询从 **73.083 秒降到 52.710 秒（约 -27.9%）**；服务 CPU 从 **54.082 降到 37.990 核秒（约 -29.8%）**。20 次独立 ingest 合并为一次，图关系阶段累计墙钟从 17.536 降到 4.221 秒。

这是同一套**预存真实向量**下的本机回环测试，验证了用户路径上的重复工作减少。没有调用 Voyage，不包含远端模型推理、公网下载或 HTTP JSON 解码，不是线上全程加速比例，也不验证检索质量。每组只有一个样本，文件缓存、调度和机器负载并未严格控制。

纯 core 回放本轮 **44.990 → 50.707 秒**，未证明更快；其 CPU 基本不变，RSS 降低。不能把线程重叠直接称为 CPU 加速，更不能宣称已逼近理论时间下限。

## 实现

- 新客户端上传/删除使用可选 `deferIndexing`，先落 blob 与持久待处理账本；上传完成后显式 flush 合并索引。旧请求默认仍同步执行。
- 复用 `ProjectIndexer` 后台线程和每项目锁，不增加任务队列基础设施。成功后清账；失败/重启保留待处理项，下一次调用即使无文件变化也重试 flush。
- 客户端确认待处理工作为零且无后台错误后才查询。上传完成后的索引等待最多 120 秒，超时返回可重试提示，服务继续。**这不是扫描、上传全过程的 120 秒总预算，也没有新增结构化“索引中”上下文包。**
- `progressOnly=true` 轮询只读进度快照；不反复开索引库或遍历 blobs。普通状态接口保留完整统计。
- 全量重建逐文件投递向量；补嵌只处理未投递的存量文件，避免双投。尾窗立即派发，SQLite 图解析与向量收尾重叠；旧向量删除仍在消费者排空后，保留按内容复用来源。
- 删除期间阻止新 worker，初始化时再次验证项目存在；锁保持进程内身份稳定。旧同步请求修复成功后清除过期的后台失败状态。

## 用户路径结果

| 指标 | 优化前 | 首版（完整状态轮询） | 轻量轮询修正后 |
|---|---:|---:|---:|
| 客户端总墙钟，秒 | 73.083 | 54.045 | **52.710** |
| 服务 CPU，核秒 | 54.082 | 45.053 | **37.990** |
| 服务峰值 RSS，MiB | 523.6 | 599.5 | **628.2** |
| ingest 次数 | 20 | 1 | **1** |
| Engine 索引入口累计墙钟，秒 | 60.879 | 43.220 | **39.510** |
| Indexer 主流程累计墙钟，秒 | 56.875 | 40.864 | **36.913** |
| 最后查询，秒 | 2.706 | 1.603 | 1.651 |
| 状态轮询次数 | 0 | 50 | 76 |
| 状态请求累计处理时间，秒 | 0 | 18.625 | **1.186** |

客户端路径 RSS 增加约 20%，这是合并一次索引的资源代价；仍在本次 2 GiB VPS 的约束内。RSS 是服务进程峰值，不是整机或整个 cgroup 峰值。查询时间为单次样本，不作为稳定的查询优化收益。

上传请求累计处理时间由 64.356 秒变为 2.894 秒；**旧上传请求包含索引，新请求只保存内容，因此这不是纯网络上传加速比例**。轻量轮询处理时间与后台索引重叠，不能从总墙钟中直接相减。

## 阶段计量

下表为累计墙钟，包含线程等待；阶段会重叠，子阶段还会被父阶段包含，**不能相加成总时间或作独占 CPU 分布**。

| 阶段 | 优化前客户端，秒 | 轻量轮询修正后，秒 |
|---|---:|---:|
| 代码解析 | 5.076 | 5.902 |
| chunk 切分 | 1.071 | 1.560 |
| SQLite 文件变更处理，含 FTS | 12.868 | 18.448 |
| 其中 FTS 写入 | 6.137 | 8.937 |
| 其中分词，包括 ASCII 快路径 | 5.344 | 6.133 |
| 本地向量处理窗口，含读取/转换/入库 | 14.477 | 20.901 |
| 其中 LanceDB upsert | 4.399 | 6.601 |
| 图关系解析 | **17.536** | **4.221** |

SQLite/向量阶段墙钟上升不能解释成“CPU 工作增加同样多”；引入重叠后争用与等待也会进入计时。明确收益来自减少重复索引/建图以及降低进度查询开销。下一轮若继续压缩时间，应先区分 SQLite/FTS、向量物化的独占 CPU、锁等待与磁盘等待，再选择改动；不直接提高并发。

未改动的扫描阶段也出现明显时间差，说明这些单样本有环境波动；不能据此证明差异全由流水线造成。但目前也没有证据支持 core 的墙钟加速。顺序回归证明 embedding 能在最后一个文件解析前启动，以及尾窗与图解析确实能重叠。
