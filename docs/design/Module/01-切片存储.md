## 0. 组件定位

一句话：**把上传的源码变成可检索的结构化资产**。

```text
输入                          本组件                          输出（被 02/03 消费）
──────                      ──────────                      ──────────
文件级 blob        →   解析(tree-sitter)          →   源码镜像 blobs/
（05 组件同步来的）       切片(Chunk)                      index.db（SQLite：
                          符号(Symbol)                      chunks/symbols/edges/
                          边(Edge)                          FTS5/unresolved_refs）
                          向量化(embed)                     vectors.lance（LanceDB）
```

**边界（不管什么）**：
- 不管检索与融合（02 组件）
- 不管 ContextPack 组装与预算（03 组件）
- 不管网络传输、增量检测协议、checkpoint（05 组件——本组件的输入就是"这批文件新增/修改/删除了"）
- 不管用户/项目鉴权（06 组件——本组件假设 project_id 已解析）

**组件内部 = 两大主题 + 一个贯穿机制**：
1. 切片策略（Chunking）——怎么切
2. 存储方案（Storage）——存哪里、什么结构
3. 增量与失效（贯穿）——变了怎么办

## 2. 第一大类：切片策略（Chunking）

### 2.1 业界方案盘点

| 方案 | 代表实现 | 原理 | 对代码检索的适配 | 成本 |
|---|---|---|---|---|
| 固定窗口机械切分 | notace（400 行/blob）、各 RAG 框架默认 | 按行/字符/token 定长切 + overlap | 差：函数拦腰截断，embedding 语义被切碎，调用关系丢失 | 极低 |
| 递归字符切分 | LangChain RecursiveCharacterTextSplitter | 按分隔符优先级（段落→行→空格）递归切到目标大小 | 中：代码场景仍是文本启发式，类/函数边界靠分隔符运气 | 低 |
| **AST/语法感知切分** | LlamaIndex CodeSplitter、CocoIndex、Cursor 索引（公开博客：分块+embedding+Merkle 增量）、codegraph/ragcode | 解析器找语法节点（函数/类），按节点边界切 | **好：语义单元完整，符号与 chunk 对齐，图可关联** | 中（需解析器，失败需兜底） |
| 语义切分 | LangChain/LlamaIndex SemanticChunker | 相邻句 embedding 相似度低于阈值处断开 | 差（对代码）：额外 embedding 成本，收益低于语法边界；适合自然语言文档 | 高 |
| 层次/父子切分 | LlamaIndex AutoMergingRetriever、SentenceWindow | 小块检索、命中后返回父块/窗口上下文 | 思想优秀：**检索粒度与阅读粒度分离** | 中 |
| LSP/Symbol 工具级 | Serena、universal-ctags | 调语言服务器取精确符号/引用 | 精度最高但重：每语言一个 LSP 进程，clangd 需 compile_commands，VPS 上多项目并发不现实 | 高 |
| 正则/trigram 索引 | Zoekt（Sourcegraph） | trigram 倒排，为正则搜索优化 | 与 RAG 正交（我们是向量+BM25+图），不适用 | — |

**结论**：AST 符号级切分是唯一同时满足 C/C++/Python 语义完整性的方案【已验证：codegraph 用它实测 C 92.2%/C++ 94.8%/Python 100% 跨文件覆盖率，Background/02 §4】。

**层次切分思想的重构**：传统 parent-child 需要两套 chunk（小块嵌入、大块存储）。nova 用**四层模型**实现同一效果且只有一份 chunk 存储——Symbol 层就是"父"，Chunk 是"子"，skeleton 渲染（03 组件）提供"父视角"。存储不冗余。

### 2.2 各语言的切片难点与规则

C/C++/Python 的坑不同，规则分开定：

#### Python（最简单，先做）

| 规则 | 内容 |
|---|---|
| 符号节点 | function_definition / class_definition / 模块级 assignment（带类型注解的才建 symbol）|
| 切法 | 函数=1 chunk（含装饰器+签名+docstring+体）；类=骨架 chunk + 每方法 1 chunk；模块级代码=兜底 chunk |
| import 解析 | 相对 import、`from x import y as z`、`__init__.py` 包语义 → edges(imports) |
| 难点 | 装饰器（跟随函数进 chunk）；动态特性不猜，解不开进 unresolved_refs【已验证：三项目共识"如实标注不猜"】 |

#### C（语义简单，工程坑多）

| 规则 | 内容 |
|---|---|
| 符号节点 | function_definition / struct_specifier / enum_specifier / typedef / 宏函数（preproc_function_def）|
| include 语义 | `#include "x.h"` 相对路径优先；`<x.h>` 按 include path 猜测（无 build 信息时尽力而为）→ 解不开标 unresolved |
| 函数指针 | `(*fp)(...)` 调用不能静态定型 → 函数指针表/赋值处合成 calls 边，provenance='synthesized'【可参考：codegraph cfnptr.rs】 |
| 宏 | 简单对象宏/函数宏建 symbol；复杂宏（token pasting）不展开，如实标注 |
| 静态链接 | static 函数仅文件内可见 → 解析时限定可见域【已验证：GitNexus static linkage 分析】 |

#### C++（最大风险项，V1 定位"尽力而为 + 诚实标注"）

| 规则 | 内容 |
|---|---|
| 符号节点 | function_definition / class_specifier / struct / namespace / template_declaration（**模板整体 1 symbol，不实例化**）|
| 重载消歧 | chunk_id 后缀消歧（见 §2.4）|
| 模板调用 | `foo<int>(x)` 解析到模板定义，实例化差异 V1 忽略 |
| 高级语义不做 | 两阶段查找、用户定义转换序列、模板约束——V1 全部不做，解析不了的调用进 unresolved_refs，**Missing Evidence 如实报告**【清单来源：GitNexus C++ 模块，仅作功能清单参考，Background/04 §6】|
| include | 同 C；V2 接 compile_commands.json（接口预留）|

#### Markdown / 文档（SpecBlock — 一等检索公民）【自研，原则源自 Task.md §9】

**设计立场**：MD 文档不是代码的附属品，而是**人类已压缩的高密度知识**——作者已完成信息筛选与组织，单位 token 信息量远超代码；README/架构文档/ADR 里一句话往往等价于几百行代码的语义。因此 MD 与代码并列为两类一等检索资产（spec evidence / code evidence），本组件负责把 MD 的结构价值完整保留进索引，供 02/03 组件放大。

四项目中没有真正的 spec→code 语义层（Background/05 §6 确认的空白），以下规则自定：

**① 文档类型识别（doctype，索引期按路径/文件名规则定型）**

| doctype | 示例 | 检索价值定位 |
|---|---|---|
| agent-instructions | AGENTS.md / CLAUDE.md / .cursorrules | 最高——写给 AI 的操作知识 |
| readme | README* | 高——项目门面，稳定 |
| design | ARCHITECTURE* / docs/design/** | 高——核心设计知识 |
| adr | docs/adr/** | 高——含决策理由 |
| api | API*.md / PROTOCOL* / openapi | 高——接口契约 |
| changelog | CHANGELOG* | 低——历史流水 |
| guide | 其余 | 中 |

doctype 是 02 rerank 与 03 预算优先级的输入信号（见本节末接口约定）。高信息密度文档（agent-instructions、design、adr、readme、api）默认提高排序优先级；但 SpecBlock 不新增独立 Planner 分支，具体召回仍复用现有 BM25/Vector 管线。

**② SpecBlock 切块：标题树小节完整块**

```text
Markdown 文件
  → front matter（YAML）单独成块
  → ATX 标题（#/##/###）构成层级树
  → SpecBlock = 一个标题下的完整小节
  → heading_path = 根到本节标题链，如 "架构 > 认证模块 > token 刷新流程"（spec 的 fqn）
```

- **不按 token 硬切小节**：解释性文本拆碎杀伤力大。超长小节（>2048 token）走三通道规则的 embedding 截断（§2.4），存储保留全文。段落级子块（parent-child 式：段落命中返回小节）列为 V2 观察项【权衡】
- **块内结构提取**：code fence 单独登记（含语言标注）——文档中的代码示例是"意图代码"，是 spec↔code 对齐的天然锚点；V1 只存不解析。表格/列表保留原文
- **embedding 文本** = `f"{doctype} | {path} | 标题链: {heading_path} | {content}"`——标题链进入向量语义空间后，"认证模块的 token 怎么刷新"这类自然语言查询直接命中

**③ spec_references：spec↔code 双向桥（本组件对检索层的最大贡献）**

```text
索引期：SpecBlock 提取 mentioned symbols（行内 code、符号名）
        → 与 symbols.name/fqn 匹配
        → spec_references(spec_block_id, symbol_id, provenance='inferred')
        匹配纪律：fqn 精确匹配优先；同名歧义时全部挂 inferred（宁多勿漏，
        下游只是弱扩展信号，错挂的代价是多余候选而非错误事实）

增量期：symbol 被删除/改名 → 级联将其 spec_references 置 stale=1
        （文档引用的符号已不存在 → 文档可能过时，V1 的文档新鲜度信号）
```

检索期它成为 calls 边之外的第二种图扩展边（02 组件消费）：代码命中 → 拉引用它的 spec 块（设计意图）；spec 命中 → 拉它提到的代码符号（实现位置）。"代码现在怎么写"与"项目要求怎么写"在检索层会师，ask_project 才能输出 Implementation vs Spec 对比。

**关键纪律（不变，D-06）**：spec↔code 关联永远是 inferred 弱引用，严禁生成 implements_spec 类强事实关系——匹配错了会系统性误导 ask_project。

**④ 对下游组件的接口约定（本组件产出的信号清单）**

| 信号 | 消费方 | 用途 |
|---|---|---|
| doctype | 02 rerank 特征 / 03 预算优先级 | 高价值文档加权；同 token 预算下 spec 块信息密度高，优先保留 |
| spec_references | 02 图扩展第二种边 | 代码↔意图双向扩展（见 ③）|
| chunk.symbol_kind 含 spec_block | 03 ContextPack 证据分列 | spec evidence 与 code evidence 分开呈现（Task.md 四分证据）|
| spec_references.stale | 03 MissingEvidence | "文档引用的符号已不存在，文档可能过时"警告 |

注意：doctype 加权是 **rerank 信号而非独立检索通道**——刻意避免 ragcode 的 15 路专门化歧途（Background/03 §3.3）；spec/code 的结果多样性配额在 03 组装层做，不在检索层做。

#### 兜底（所有语言）

解析失败/不支持的语言：递归字符切分，800 行上限，chunk 标记 symbol_kind='fallback_block'，evidence tier 天然降低（02 组件按 kind 降权）。

### 2.3 四层模型（正式定义）

```text
Layer 1  SourceFile     源码镜像，content-addressed，不可变，一切索引的源头
Layer 2  Symbol         图节点：name/fqn/kind/位置/可见性；跨文件解析的主体
Layer 3  Chunk          检索单元：一个符号的完整切片；BM25/向量/图三索引的共同主体
Layer 4  Index Views    三种视图：FTS5 / LanceDB / edges —— 全部可从 1-3 层重算
```

依赖方向单向：4 ← 3 ← 2 ← 1。**改切片策略不动 Source，换 embedding 模型不动 Symbol/Edge**——分层失效的基础（§4）。

### 2.4 Chunk 细节设计

**chunk_id 与稳定性【权衡】**

```text
chunk_id = {path}:{symbol_fqn}:{start_line}
```

**Hash 语义（D-43）**：

- `blob_hash`：源码镜像与同步使用，定义为 `sha256(path_bytes || 0x00 || content_bytes)`；路径和内容边界固定，避免拼接歧义。
- `files.content_hash`：仅对文件原始内容计算 `sha256(content_bytes)`，用于文件级变更检测。
- `chunks.content_hash`：仅对规范化后的完整切片内容计算 hash，用于 chunk 级向量复用。

三者用途不同，不能用任一 hash 替代其他 hash；Module/05 的同步协议只传递 blob_hash，Module/01 的索引增量使用文件和 chunk content_hash。

- 同名重载：start_line 天然消歧（必然唯一）
- **不追求跨代稳定**：ID 只需"同一代索引内唯一"。理由：向量缓存用 content_hash 对账（不用 ID），边在文件重解析时整体重建（无跨代引用）。GitNexus 追求 ID 稳定是因为它的 embedding 缓存跨代存在，nova 不背这个包袱【对比：GitNexus arity/type-hash 方案的代价，Background/04 §2】

**三通道差异化输入（同一 chunk，三个消费者吃不同内容）**

| 通道 | 输入 | 理由 |
|---|---|---|
| SQLite 存储 | 完整函数体 | 03 组件渲染 skeleton 需要全文 |
| FTS5/BM25 | 完整函数体 | BM25 不怕长文档，词频统计需要全文 |
| embedding | signature + docstring + 截断体（≤2048 token） | 超长函数尾部贡献递减，截断省成本防语义稀释 |
| 渲染（03） | 按需 skeleton（签名+首尾 N 行+elided 计数） | 预算控制 |

**尺寸目标**：典型函数 chunk 30-200 行；类骨架 chunk 恒小；无硬上限——超长函数靠三通道差异化消化，而不是拆碎存储【已验证：ragcode expansionLevel 模式】。

## 3. 第二大类：存储方案（Storage）

### 3.1 业界方案盘点

**关系/结构存储维度**

| 方案 | 形态 | 评估（对 nova） |
|---|---|---|
| SQLite（FTS5 + 边表） | 嵌入式单文件 | 【已验证】codegraph/ragcode 双验证；零运维；FTS5 自带 BM25 |
| PostgreSQL + pgvector | 服务端 | 元数据管理强；但 C2（单 VPS）下多一个常驻进程；项目删除需清表 |
| DuckDB | 嵌入式分析库 | OLAP 取向，点查/小事务非所长 |

**向量维度**

| 方案 | 形态 | 评估 |
|---|---|---|
| **LanceDB** | 嵌入式列存 + IVF_PQ ANN | 【已验证】ragcode 生产使用；per-project 目录天然匹配 C3 隔离 |
| sqlite-vec | SQLite 扩展 | 最优雅（向量进同一个 .db），但大规模 ANN 成熟度弱；列为观察项【权衡】 |
| pgvector | PG 内 | 同 PG 评估 |
| Qdrant/Milvus/Weaviate | 独立服务 | 违反 C2，V1 排除 |

**图维度**

| 方案 | 形态 | 评估 |
|---|---|---|
| **SQLite 边表** | edges 表 + 索引 | 【已验证】codegraph 百万级边生产使用；递归 CTE 做多跳查询 |
| Kuzu / LadybugDB | 嵌入式图数据库（Cypher） | GitNexus 用 LadybugDB【已验证】，但引入新组件且版本 0.x；边表够用时不必上 |
| Neo4j | 服务端 | 违反 C2 |

**源码镜像维度**：文件系统 content-addressed 目录（git 风格 sha 分片）vs 对象存储（S3/MinIO）。单 VPS 用文件系统，最简单【权衡：未来多机才需要对象存储】。

### 3.2 决策分析：为什么是"per-project 目录树"

三个候选架构：

| 架构 | 描述 | 问题 |
|---|---|---|
| A. 单一 PG 全家桶 | 所有项目共库，表带 project_id | 删除项目=多表清理；隔离靠 WHERE 子句（漏写=数据泄露，违反 C3）；PG+pgvector 常驻进程 |
| B. 单库多 schema | 每项目一个 schema | 仍是 A 的变体，迁移/备份碎 |
| **C. per-project 目录树** | 每项目独立目录：blobs+SQLite+LanceDB | **删除=rm -rf；备份=tar；隔离=OS 文件权限；故障域=单项目**（全中 C2/C3） |

C 的代价：跨项目检索难（V1 不需要）、全局统计要遍历（元数据库解决，见 §3.3）。**选 C**。

### 3.3 推荐存储架构（正式设计）

```text
~/.nova/                                   # 服务端数据根
├── nova-meta.db                           # 全局元数据库（SQLite，V1）
│     users / projects / api_tokens /
│     sync_state / usage_stats             # 结构见 06 组件，此处只引用
└── projects/
    └── {project_id}/                      # 一个项目 = 一个自包含目录【权衡：项目粒度=一个 repo】
        ├── blobs/                         # Layer 1 源码镜像
        │   └── ab/cdef1234...             # content-addressed，sha256 分片两位
        ├── index.db                       # Layer 2-3 结构库（SQLite + FTS5）
        └── vectors/                       # Layer 4 向量（LanceDB 目录）
```

**index.db 完整 DDL（v1）**：

```sql
PRAGMA journal_mode = WAL;

-- 索引配置指纹：变更触发分层重建（见 §4.2）
CREATE TABLE index_config (
    key TEXT PRIMARY KEY,          -- parser_config_hash / embedding_model / embedding_dim / schema_version
    value TEXT NOT NULL
);

CREATE TABLE files (
    path TEXT PRIMARY KEY,
    content_hash TEXT NOT NULL,        -- sha256(文件原始内容)；不与 blob_hash 混用
    language TEXT NOT NULL,
    generated INTEGER DEFAULT 0,
    branch TEXT, commit_id TEXT,
    indexed_at INTEGER NOT NULL,
    parse_errors TEXT                  -- JSON 数组：树解析警告（不是失败，失败不建行）
);

CREATE TABLE chunks (
    id TEXT PRIMARY KEY,               -- {path}:{symbol_fqn}:{start_line}
    file_path TEXT NOT NULL,
    symbol_fqn TEXT, symbol_kind TEXT, -- function/method/class_skeleton/spec_block/fallback_block
    start_line INTEGER, end_line INTEGER,
    signature TEXT, docstring TEXT,
    content TEXT NOT NULL,
    content_hash TEXT NOT NULL          -- 增量单位：chunk 级
);
CREATE INDEX idx_chunks_file ON chunks(file_path);
CREATE INDEX idx_chunks_kind ON chunks(symbol_kind);

CREATE TABLE symbols (
    id TEXT PRIMARY KEY,               -- {path}:{fqn}:{start_line}
    name TEXT NOT NULL, fqn TEXT NOT NULL, kind TEXT NOT NULL,
    chunk_id TEXT, file_path TEXT,
    start_line INTEGER, end_line INTEGER,
    is_exported INTEGER DEFAULT 0
);
CREATE INDEX idx_symbols_name ON symbols(name);
CREATE INDEX idx_symbols_fqn ON symbols(fqn);

CREATE TABLE edges (
    source TEXT NOT NULL, target TEXT NOT NULL,
    kind TEXT NOT NULL,                -- calls/imports/exports/extends/implements/
                                       -- references/contains/instantiates/overrides
    line INTEGER,
    provenance TEXT DEFAULT 'parsed'   -- parsed / synthesized
);
-- 边唯一性：codegraph #1034 教训，重复边会污染 callers/impact
CREATE UNIQUE INDEX idx_edges_identity
  ON edges(source, target, kind, IFNULL(line, -1));
CREATE INDEX idx_edges_target_kind ON edges(target, kind);
CREATE INDEX idx_edges_source_kind ON edges(source, kind);

CREATE TABLE unresolved_refs (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    from_symbol TEXT NOT NULL,
    reference_name TEXT NOT NULL,
    reference_kind TEXT NOT NULL,
    line INTEGER, file_path TEXT, language TEXT,
    status TEXT DEFAULT 'pending',     -- pending / failed（resolved 即删行）
    name_tail TEXT DEFAULT ''          -- 'util.greet'→'greet'，failed 重试的匹配键
);
CREATE INDEX idx_unresolved_failed ON unresolved_refs(name_tail) WHERE status='failed';

CREATE TABLE spec_blocks (             -- Markdown SpecBlock（§2.2，一等检索公民）
    id TEXT PRIMARY KEY,
    file_path TEXT NOT NULL,
    doctype TEXT NOT NULL,             -- agent-instructions/readme/design/adr/api/changelog/guide
    heading TEXT, heading_path TEXT,   -- "架构 > 认证模块 > token 刷新流程"
    heading_level INTEGER,
    start_line INTEGER, end_line INTEGER,
    content TEXT NOT NULL,
    code_fences TEXT                   -- JSON 数组 [{lang, content, line}]：意图代码锚点，V1 只存不解析
);
CREATE INDEX idx_spec_doctype ON spec_blocks(doctype);

CREATE TABLE spec_references (         -- spec↔code 双向桥（§2.2 ③）
    spec_block_id TEXT NOT NULL,
    symbol_id TEXT NOT NULL,           -- 直接外键挂 symbol（v2 重设计，原为泛化字符串）
    provenance TEXT DEFAULT 'inferred',-- 永远 inferred（D-06），永不升级为强事实
    stale INTEGER DEFAULT 0            -- symbol 删除/改名时增量期级联置 1
);
CREATE INDEX idx_spec_refs_symbol ON spec_references(symbol_id);
CREATE INDEX idx_spec_refs_stale ON spec_references(spec_block_id) WHERE stale = 1;

-- BM25：外部内容表 + 触发器同步（FTS5 content= 模式）
-- CJK 修正（v2.1，由 Module/02 评审发现）：unicode61 对中文不分词（整句单 token，
-- 中文查询失效）。方案：索引与查询双侧同库预分词（分词器为独立模块，
-- 见 Module/02 §4.2-b），分词结果空格连接后写入 content 列。
CREATE VIRTUAL TABLE chunks_fts USING fts5(
    content, signature, docstring, file_path,
    content='chunks', content_rowid='rowid', tokenize='unicode61'
);
-- （chunks.content 存原文供渲染；FTS 的 content 列由写入器先过 CJK 分词再空格连接。
--  触发器定义同 codegraph 模式：INSERT/UPDATE/DELETE 三触发器，略）
```

**vectors/（LanceDB）**：单表 `chunk_vectors`：`chunk_id (主键) + vector + content_hash`。generation 直接整表重建（Lance 表的原子 replace），不需要 ragcode 的 prepare/validate/commit 三段式——那是为"同库内换表"设计的，per-project 目录 + 表级 replace 更简单【权衡：简化自已验证方案】。

### 3.4 容量估算（量级，供 VPS 规划）

以 100 万行 C/C++/Python 混合代码为基准（约 30-80K 函数符号）：

| 数据 | 估算 | 说明 |
|---|---|---|
| blobs/ | ≈ 源码体积（40-80MB） | 压缩源（git 风格可加 zlib）减半 |
| index.db | 150-300MB | chunks 全文 + FTS5 是大头 |
| vectors/ | 50-120MB | 50K chunk × 384D float32 ≈ 1.5KB/条 |
| **合计** | **< 500MB / 百万行** | 200GB VPS 可承载数百个中型项目 |

## 4. 贯穿机制：增量与失效

### 4.1 双层增量【已验证：ragcode + notace 组合】

```text
05 组件送来变更集 {added[], modified[], deleted[]}
  │
  ├─ deleted → 删 files/chunks/symbols/edges 行 + 级联清 FTS + 删向量
  │            + 级联置 spec_references.stale=1（引用被删符号的文档标记过时）
  ├─ added/modified（file.content_hash 变了才进来）
  │    → 重解析该文件 → 新旧 chunks 按 content_hash 对账：
  │        hash 相同 → 保留（向量复用，零成本）
  │        hash 新增 → 写行 + 嵌入
  │        hash 消失 → 删行 + 删向量
  │    → 该文件的 edges 整体重建（无所谓增量，单文件边量小）
  │    → 该文件产生的 unresolved_refs 重写
  └─ 全局二遍解析：pending refs 重新尝试（新增符号可能解开旧 failed）
```

效果：改 1 个函数 → 重嵌入 1 个 chunk。【已验证：ragcode generation 机制的效果主张】

### 4.2 配置指纹与分层失效（关键，防"策略升级留下脏索引"）

```text
index_config 三级指纹，各自独立失效：
  parser_config_hash 变了  → 全量重解析 + 重切 + 重嵌（AST 层重建）
  embedding_model/dim 变了 → 只重嵌入（AST/Symbol/Edge 原样，向量层重建）
  都没变                   → 只走 §4.1 增量
```

【已验证：notace 的 chunking config_hash 思想（Background/01 §3.2）扩展为两级】。这让"升级切片规则"成为服务端自主操作：改配置 → 指纹变 → 按项目排队重算，用户无感。这正是 C4（Source Mirror）买来的核心能力。

### 4.3 时序（一次增量索引）

```text
T0     收到变更集（N 个文件）
T0+    逐文件：读取 blob → tree-sitter 解析（Rust 侧，<10ms/文件量级）
       → 切片/符号/边 → 事务写入 index.db
T1     二遍解析 unresolved_refs（只处理 pending + 相关 failed）
T2     增量嵌入变更 chunks（批量调 embedding API）
T3     更新 files.indexed_at / sync_state → 通知 05 组件完成
```

索引并发模型：每项目一个写者（SQLite WAL 单写多读），多项目天然并行；项目内解析可再开 worker 池（codegraph parse-pool 模式，V1 可先串行）。

## 5. V1 明确不做（边界）

| 不做 | 理由 | 何时做 |
|---|---|---|
| code fence 意图代码解析 | 存储锚点已够 rerank/扩展用，解析成符号调用是 V2+ 的事 | spec 检索质量有诉求时 |
| LSP 接入 | VPS 多项目并发不现实；tree-sitter 覆盖 90%+ 场景 | V2，作为 Code Intelligence Provider 第二实现 |
| compile_commands.json | 需要 build 系统集成，C1 场景先靠 include 猜测+unresolved 标注 | V2（接口预留：include 解析器独立模块） |
| 模板实例化 / C++ 两阶段查找 | 投入产出比 V1 不成立 | 按用户反馈排期 |
| sqlite-vec 替代 LanceDB | ANN 成熟度不够 | 观察项 |
| 对象存储（S3/MinIO） | 单 VPS 文件系统够 | 多机部署时 |
| 跨项目合并检索 | 无场景 | 有需求再说 |
| zlib 压缩 blobs | 优先简单 | 容量吃紧时（一天工作量） |

## 6. 开放问题（评审待定）

0. **SpecBlock 段落级子块**：超长小节是否引入 parent-child 式子块（段落命中返回小节）——V1 已定不做（embedding 截断够用），V2 按 spec 检索的实际召回质量决定。
